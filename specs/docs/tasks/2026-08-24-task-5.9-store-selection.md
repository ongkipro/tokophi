# Task 5.9 — Multi-Store Selection Explicit and Deterministic (F-T10)

**Date:** 2026-08-24 · **Executor:** Lane A (Claude subagent) · **Branch:** `feat/task-5.9-store-selection`

## What was wrong

Measured 2026-08-23: a user with memberships in two stores landed on an **arbitrary** store at
login. `findLogin` (`apps/admin/lib/auth.ts`) inner-joined `store_users` with `limit(1)` and **no
ORDER BY**, so which membership won was query-plan-dependent. The topbar store dropdown rendered a
mock `STORES` list and only ever showed the session store — the second real membership was
unreachable from the UI.

## The contract

`apps/admin/lib/store-selection.ts` owns it, in one place (`membershipOrder()`):

> **The default membership is the earliest `invited_at` (nulls last), tie-broken by ascending
> store id.**

Every reader — `findLoginRow` (which `auth.ts` re-exports as `findLogin`) and `listMemberships`
(the switcher's data source) — sorts by that one definition. A pinning test refuses a second,
unordered copy in `auth.ts`.

## The moving parts

| Piece | File | Behaviour |
|---|---|---|
| Deterministic login default | `lib/store-selection.ts` `findLoginRow` | LEFT join user → default membership in contract order; `storeId: null` for a zero-membership account |
| Clear no-membership refusal | `lib/actions/auth.ts` `signIn` | password-valid + no membership ⇒ "Akun ini tidak punya akses ke toko mana pun…" (before the 2FA round-trip), never the wrong-password lie |
| Switch | `lib/actions/store.ts` `switchStore` | proves membership in the TARGET store against `store_users` **in the same action**, then re-mints the session cookie server-side; role from the target row; refuses impersonated sessions and non-UUID ids |
| Switcher UI | `components/admin/topbar.tsx` + `app/(admin)/layout.tsx` | lists EVERY live membership (`listMemberships(session.userId)`), current store checked; picking another calls `switchStore` and lands on `/store/{slug}` |
| Revocation | `lib/auth.ts` `getSession` (unchanged) | membership re-read per request; row deleted ⇒ session null ⇒ layout redirects to `/api/auth/signout` — **deliberately not weakened** |

## Verification

- **Vitest (real PostgreSQL):** `apps/admin/lib/store-selection.test.ts` — 11 tests: deterministic
  pick, tie-break, NULL `invited_at` last, member/non-member resolution, revocation fallback,
  zero-membership shape, plus `codeOnly` source claims on the action wiring. **Mutation proof:**
  ORDER BY flipped to `desc nulls first` ⇒ 3 reds; restored ⇒ green.
- **Full suite:** `npx vitest run` → **128 files / 1076 tests passing** (baseline 127/1065).
- **Typecheck:** `npx tsc --noEmit -p apps/admin` → exit 0.
- **Browser, production build** (`next build` + `next start :3216`, throwaway 2-membership user):
  login → `/store/kopi-senja` (earliest invitation) · switcher lists both stores (screenshot) ·
  switch → `/store/hijab-amara`, topbar renamed · SQL-delete of the current membership + reload →
  clean signout to `/login`, **zero 5xx** · re-login → surviving store. Probe rows deleted after.

## Boundaries / traps for the next agent

- The switch **re-mints** a full-length session; that is by design — the caller already held a
  live, revocation-checked session, and `getSession` keeps re-validating per request.
- Switching under impersonation is refused: the consumed grant was for ONE store. Not driven in a
  browser; guarded by the action's `session.imp` check + source claim.
- Do not add a second ORDER BY copy anywhere: import `membershipOrder()` from
  `lib/store-selection.ts`.
- `findLogin` is now a LEFT join — membership fields are nullable; `signIn` is the only caller and
  guards before minting.
