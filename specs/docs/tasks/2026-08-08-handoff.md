## How I got things wrong — six times, one shape

Every mistake last session was **inferring state from configuration, memory, or a doc instead of
observing the system**:

- deploy "broken" → never read the webhook's reply (it said `watch_paths`)
- "no `.id` anywhere" → grepped the repo, never `curl`ed a `.id` host (live for three weeks)
- "priority 1 is free" → assumed; another live app was already there
- SEC-4 "the selectors must be wrong" → the account simply did not exist
- "the merchant's DNS is correct" → trusted `verified_at` instead of asking DNS
- **the whole `.com`/`.cc` episode** → trusted `CUSTOM_DOMAIN.md` (15 July) over the code. `DEPLOY.md`
  had been right all along. **I chose a doc by its name instead of checking which one the code agreed
  with.** It cost objects created in the wrong Cloudflare zone and a merchant given the wrong target.

Twice the *checks themselves* were the bug: a pipe swallowed `npm`'s exit status so a failed build still
committed, and a "test" threw on `DATABASE_URL` before any assertion ran — failing for the wrong reason
and looking like proof.

**Two rules that would have prevented all of it:**
- Before writing that something is broken, run the one command that would prove it works.
- **Mutation-test every guard.** Break the logic on purpose and confirm it goes red *for the reason you
  expect*. A guard nobody has seen fail is a guard nobody knows works.

⚠️ And when correcting a record: a correction note must keep naming the **wrong** value, because the
wrong value is its subject. **Never sweep a history file** — a blanket replace turned a measured DNS
result into a falsehood on 2026-08-08 and had to be reverted.
