### T-3 — `.id` needs its OWN origin certificate before `strict` is even possible
- Primary requirement: SEC-2
- ✅ **DONE 2026-08-07 — and the diagnosis was the whole job.**
  The certificate Traefik served for `.id` was its **`defaultCertificate`** — the one that exists because
  Let's Encrypt cannot issue a wildcard over HTTP-01, so every host without a cert of its own gets it.
  Its SAN was `*.tokophi.com` + `tokophi.com` **only**. Cloudflare accepted it purely because `.id` ran
  `ssl: full`, which does not validate the origin. **`full` there was load-bearing, not laziness.**
- What was done, in an order chosen so nothing already working could break:
  1. Key + CSR generated **on the box** (`*.tokophi.id`, `tokophi.id`) — the private key never left it.
  2. Signed by Cloudflare Origin CA (valid to 2041). The zone had **zero** certificates before this.
  3. Installed as a **second** certificate and appended to Traefik's `certificates:` list. The
     `defaultCertificate` was deliberately left as `.com`, so nothing that worked before depended on
     the change; SNI selects.
  4. `ssl: full` → `strict`, with an automatic revert wired into the same command had any host gone red.
- Verified from outside: `.id` hosts serve `DNS:*.tokophi.id, DNS:tokophi.id`; `.com` hosts still serve
  `DNS:*.tokophi.com, DNS:tokophi.com`; five `.id` storefronts 200; `.com` 200/307/200.
- Checked, not assumed, at each step: the CSR's SAN before signing (the first grep read the wrong line),
  cert/key modulus equality, YAML re-parse after the edit, and a backup at
  `/root/idcert/tokophi-origin-tls.yaml.bak`.
- 🔴 **What this actually closed:** traffic carrying checkout and buyer data was reaching an origin whose
  certificate was not validated. It now is.
- Done when: still passes; run both halves, because the second is the regression that would matter —
  ```bash
  openssl s_client -connect 45.77.33.112:443 -servername zanobyshop.tokophi.id </dev/null 2>/dev/null \
    | openssl x509 -noout -ext subjectAltName    # → DNS:*.tokophi.id, DNS:tokophi.id
  openssl s_client -connect 45.77.33.112:443 -servername toko.tokophi.com </dev/null 2>/dev/null \
    | openssl x509 -noout -ext subjectAltName    # → DNS:*.tokophi.com, DNS:tokophi.com  (unchanged)
  ```
  ⚠️ Rollback, if it is ever needed: `/root/idcert/tokophi-origin-tls.yaml.bak`, then set the zone's
  `ssl` back to `full` — in that order, because `strict` without the certificate is what breaks it.

>
> | | what happens to `permata-store` / `valoish-store` |

> | **B-hard** | the renderer ignores stored templates; their built homepage stops being served |
>
> ⚠️ **B-hard destroys work two merchants did, without deleting a row** — so it leaves no trace, cannot

> The code has a documented position here; overruling it is allowed, but it should be **deliberate**.
>
> The **1:1 image lock (UX-2) is not affected by this fork** — that one is genuinely global, applies to

>
> The platform default is what every storefront renders. A store's own `page_templates` rows **stop
> being served**, including the three that have them today.
>
> ⚠️ **This ends the serving of homepages `permata-store` and `valoish-store` actually built.** That is
> now a decision, not an accident — but it must be built so it is **reversible and visible**:
> - **Do NOT delete their rows.** B-hard is a render-time rule; the rows are the only record that
>   those two merchants ever built anything, and the only way back if this is reconsidered.
> - Whoever implements it should be able to point at the switch that turns it off.
>
> This overrules the stance in `index.astro:172` (*"that would be us editing their homepage"*)
> deliberately and with the owner's explicit instruction — noted here so the next reader does not
> treat the surviving comment as still-current policy, or "fix" the behaviour back.


- Status: Accepted — decision taken 2026-08-07 (owner chose **B** over **A**)
- Owner: Platform owner
- Source: owner request, "setup default /tema batik-nusantara dipakai semua tenant, live maupun yang
  mendaftar nanti"
- Statement: A store with no theme of its own shall render the platform default; a store that has
  customised its theme shall keep what it customised until it is deliberately reset.
- **The decision, and why B.** Two readings were on the table:
  **A — copy the rows** into every store (6 stores × 3 templates = 18 rows today). It matches the
  words "timpa dan replace", and it satisfies the request *on the day it runs*. Then it drifts: the

  twice (AGENTS.md).
  **B — one platform default, read at render** unless the store overrides it. No copying, no
  divergence, and a later theme fix reaches every tenant at once — including ones that do not exist
  yet. **B is the only one that keeps the promise the request actually makes.**
- Observed 2026-08-07, the state this has to work over:

  | `permata-store` | homepage 27 B | empty shell, nothing to lose |
  | `zanobyshop` · `beautyinyu` · `difa-pack` | none at all | 3 of 6 stores have no template |

- ✅ **Backup already taken before any of this runs**, verified to contain all five rows:

- ⚠️ **`valoish-store` is the one judgement call left in this task.** Under B it does not have to be

## DEL-3 — A merge to `main` can fail to produce a deploy, silently

- Status: Open
- Owner: Platform owner
- Source: measured 2026-08-07 while watching the merge of #191
- Statement: When `origin/main` moves, production shall follow it, or something shall say that it did
  not.
- Observed: `origin/main` sat at `381a8e7` for **25+ minutes** while all three containers stayed on
  `b22c1ec` — one commit behind. **No image for `381a8e7` was ever built** (newest built:
  `b22c1ec`). No build running, no unhealthy container, disk 58 % with 69 G free. **All four hosts
  green the entire time.**
- Observed, and it is one clue rather than a root cause: Coolify's recent log shows only
  `App\Jobs\ProcessGithubPullRequestWebhook` — a **pull request** webhook job, not a push. Coolify
  deploys on push. Earlier merges the same day *did* deploy automatically, so this is not a settled
  diagnosis and must not be written up as one. Reading the deployment queue needs Coolify API access;
  the token on file is Unauthenticated (`DEPLOY.md`).
- 🔴 Why it matters more than it looks: **the site stays green on older code.** #191 was docs-only, so
  nothing was lost — but the same silence over a checkout fix would have everyone reading
  "200/307/307/200" as proof it shipped. This is the shape of every defect worth finding here: a real
  gap behind a healthy signal.
- ⚠️ It was found by the **corrected** deploy watch (compare containers to `origin/main`). The old
  recipe — waiting for your own merge sha — fails identically whether the deploy is late or never
  happening, so it would have been dismissed as the same artefact again. The correction earned its
  keep within hours.

> ### 🔴 UPDATE 2026-08-07 — THIS IS **TWO** FAILURE MODES, NOT ONE. T-11 covers only the first.
>
> | # | mode | what it looks like | caught by T-11? |
> |---|---|---|---|
> | 1 | **Queue wedges** | a row sits `in_progress` with no build behind it; the serial queue stalls and every later merge waits | ✅ yes |
> | 2 | **Event never arrives** | the merge produces **no queue row at all**; nothing is stalled because nothing was ever asked for | ❌ **no** |
>
> **Measured, an hour apart, same configuration:** `f6fcb79` queued normally at 02:57 and finished.
> `ab7aa71` — the very next merge — **never entered the queue**: `last_queue` still read
> `[f6fcb79 finished]`, `queued=0`, while `origin/main` was `ab7aa71` and the container `f6fcb79`.
>
> ⚠️ **T-11 correctly reported `OK`, and that is the design working, not failing.** Nothing was
> wedged. Its scope note — *"does NOT claim to catch 'main moved but nothing was ever queued'"* — was
> written the night before and the uncovered case arrived within the hour. Had the claim been widened
> to sound more useful, that `OK` would have read as "everything shipped" while production sat a
> commit behind. **A narrow alarm that is honest beats a broad one that is occasionally wrong.**
>
> ⚠️ **And it revives a lead I had called a dead end.** On 2026-08-06 the missing repo webhook was
> dismissed because `auto_deploy=true` and deploys were working — correct at the time. Mode 2 is
> evidence the delivery path itself is intermittent: two consecutive merges, identical config, one
> registered and one not. Look at the **GitHub App installation and Coolify's source config**, not at
> repo webhooks (there are none, by design — Coolify connects as an App).
>
> ### ⛔ RETRACTED IN FULL 2026-08-07 — **THERE IS NO MODE 2. THERE IS NO BUG. I WAS WRONG TWICE.**
>
> Everything below about a "dead delivery path" is **false** and is kept only so nobody re-derives it.
> I asked GitHub for the actual webhook deliveries. They arrive, and **Coolify answers `200 OK`**:
>
> ```json
> {"status":"failed","message":"Changed files do not match watch paths. Ignoring deployment.",
>  "application_name":"tokophi",
>  "details":{"changed_files":["specs/docs/tasks/2026-08-06-open-work.md"],
>             "watch_paths":["!**/*.md"]}}
> ```
>
> **The application has a watch path of `!**/*.md`.** `ab7aa71`, `6930ac0`, `e64c4f4` and `9e92281`
> were **every one of them docs-only**, so Coolify skipped them **exactly as configured**. The GitHub
> App is healthy: `/app` → 200, the installation covers `ongkipro/tokophi` (53 repos), and every
> `push` delivery is `OK (200)`.
>
> **How I got here — the actual lesson, which is worth more than the finding was:**
> 1. I compared the running container to `origin/main`, saw a gap, and called it a failure. **I never
>    established that "container == main" was supposed to be true.** It is not, by design.
> 2. I then "confirmed" it by watching the gap persist over three more merges — **all four of which
>    were docs.** I mistook a constant cause for corroboration. More samples of the same mistake felt
>    like evidence and were not.
> 3. The one question that would have ended it on the first day — *what did the webhook actually
>    reply?* — I never asked, because the earlier wedged-queue incident had given me a ready story to

### T-11 — Alarm on a production that has fallen behind `main`
- Primary requirement: DEL-3
- ✅ **DONE 2026-08-07.** `ops/check-deploy-currency.sh`, installed as
  `/usr/local/bin/tokophi-deploy-currency` and run every 10 min by
  `/etc/cron.d/tokophi-deploy-currency` — because a script nobody runs is not a gate.
- 🔴 **ROOT CAUSE, measured, replacing the guess this task was filed on.** A row sat `in_progress`
  from 2026-08-06 21:17 with no build process behind it. Coolify runs an application's queue
  **serially**, so every later merge simply waited: no build, no image, nothing unhealthy, four hosts
  green for hours on the previous commit. The webhook, the GitHub App, `auto_deploy` and the branch
  were all **correct** — do not go looking there. (It later cleared on its own, so it can recur;
  that is precisely why this alarm exists rather than a one-off fix.)
- What it checks, and what it deliberately does not: it reads **only Coolify's own database on the
  box** — no GitHub token, no egress, nothing to expire — so it catches a **wedged or piled-up
  queue**, the failure that actually happened. It does **not** claim to catch "main moved but nothing
  was ever queued". Say what you check and no more.
- ⚠️ **L1 cannot see this.** L1 asks "is a container running?" — it was, correctly, on old code. This
  asks "is it the RIGHT code?". Neither answers the other, which is why it is a second alarm and not
  an extension of the first.
- Done when: running it on a healthy box exits 0 and prints the running sha beside the last queue row —
  ```bash
  ssh -i ~/.ssh/tokophi_dev root@45.77.33.112 /usr/local/bin/tokophi-deploy-currency
  # → running=<sha>  last_queue=[<sha> finished <ts>]  queued=0
  # → OK: no wedged or piled-up deployment.      (exit 0)
  ```
- ⚠️ **Honest limit on the evidence.** The healthy path is proven end to end (exit 0 via the real cron
  path). The ALARM branch is **not** proven end to end: doing so needs a fake `in_progress` row in the
  production queue, which was not worth the risk. What *was* proven is the predicate underneath it —
  the identical query with the status swapped returns **368** rows, so the `application_id` filter and
  the age interval both work and the alarm is a `-gt 0` over that count. **Whoever next has a
  disposable Coolify: insert a stale row and watch it exit 1.** A guard never seen red is green for
  reasons nobody has checked.

### T-12 — Catch the merge that never reached the queue
- ⛔ **WITHDRAWN 2026-08-07 — built on a false premise (see the retraction under DEL-3).**
  Do not implement as written: it would alarm on every docs-only merge. Reopen only with the
  comparison rebased onto watch-path-relevant commits.
- Primary requirement: DEL-3
- Dependencies: T-11 (this is its declared blind spot, not a replacement for it)
- Done when: a check on the box resolves `origin/main` and compares it to the running container sha,
  going loud when they differ for more than ~25 minutes —
  ```bash
  MAIN=$(git ls-remote https://<token>@github.com/ongkipro/tokophi refs/heads/main | cut -f1)
  RUN=$(docker inspect -f '{{.Config.Image}}' "$(docker ps --format '{{.Names}}' | grep -m1 '^admin-')" | sed 's/.*://')
  [ "$MAIN" = "$RUN" ] || echo "PRODUCTION IS BEHIND main"
  ```
- ⚠️ It needs a **read-only** credential for a private repo. That is the whole reason T-11 stopped
  short of it: an alarm that expires with a token is an alarm that goes quiet without telling anyone.
  Whatever is used must fail LOUD when it cannot authenticate, never silently report agreement.
