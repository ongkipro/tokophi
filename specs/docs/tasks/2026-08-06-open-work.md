- Status: Open — needs the owner

- Observed: `getStoreBySlug` (`apps/storefront/src/data/store.ts`) filters on the slug and nothing

- Observed: **not exploited today** — production holds 6 stores, all `approved_at` set and none

  and brand impersonation on our own domain.
- Constraints: SEC-2
- Blocked on a decision, not on code: **404**, a neutral "belum aktif" page, or serve normally? A 404
  leaks least and tells a legitimate new merchant nothing.

### T-3 — `.id` needs its OWN origin certificate before `strict` is even possible
- Primary requirement: SEC-2
- ✅ **DONE 2026-08-07 — and the diagnosis was the whole job.**
  The certificate Traefik served for `.id` was its **`defaultCertificate`** — the one that exists because
  Let's Encrypt cannot issue a wildcard over HTTP-01, so every host without a cert of its own gets it.
  Its SAN was `*.tokophi.com` + `tokophi.com` **only**. Cloudflare accepted it purely because `.id` ran
  `ssl: full`, which does not validate the origin. **`full` there was load-bearing, not laziness.**
- What was done, in an order chosen so nothing already working could break:
  1. Key + CSR generated **on the box** (`*.tokophi.id`, `tokophi.id`) — the private key never left it.
  2. Signed by Cloudflare Origin CA (valid to 2041). The zone had **zero** certificates before this.
  3. Installed as a **second** certificate and appended to Traefik's `certificates:` list. The
     `defaultCertificate` was deliberately left as `.com`, so nothing that worked before depended on
     the change; SNI selects.
  4. `ssl: full` → `strict`, with an automatic revert wired into the same command had any host gone red.
- Verified from outside: `.id` hosts serve `DNS:*.tokophi.id, DNS:tokophi.id`; `.com` hosts still serve
  `DNS:*.tokophi.com, DNS:tokophi.com`; five `.id` storefronts 200; `.com` 200/307/200.
- Checked, not assumed, at each step: the CSR's SAN before signing (the first grep read the wrong line),
  cert/key modulus equality, YAML re-parse after the edit, and a backup at
  `/root/idcert/tokophi-origin-tls.yaml.bak`.
- 🔴 **What this actually closed:** traffic carrying checkout and buyer data was reaching an origin whose
  certificate was not validated. It now is.
- Done when: still passes; run both halves, because the second is the regression that would matter —
  ```bash
  openssl s_client -connect 45.77.33.112:443 -servername zanobyshop.tokophi.id </dev/null 2>/dev/null \
    | openssl x509 -noout -ext subjectAltName    # → DNS:*.tokophi.id, DNS:tokophi.id
  openssl s_client -connect 45.77.33.112:443 -servername toko.tokophi.com </dev/null 2>/dev/null \
    | openssl x509 -noout -ext subjectAltName    # → DNS:*.tokophi.com, DNS:tokophi.com  (unchanged)
  ```
  ⚠️ Rollback, if it is ever needed: `/root/idcert/tokophi-origin-tls.yaml.bak`, then set the zone's
  `ssl` back to `full` — in that order, because `strict` without the certificate is what breaks it.

- Source: owner request, "setup default /tema batik-nusantara dipakai semua tenant, live maupun yang

copy its rows once into a platform-owned holder instead of pointing at it live.

**Off-switch:** an env var read in `getStoreTemplates`, defaulting **OFF**. Ship it off, verify the
render on one store, then flip. Do not make the first deploy of this the one that changes all 7.

**Do NOT delete any store's rows** — B-hard is render-time only. `permata-store` and `valoish-store`
keep theirs, unserved, as the sole record they built anything and the only way back.

`apps/admin/lib/actions/domain.ts` proves ownership its own way and then rests at `provisioning`

chain, do not match addresses.

## SEC-6 — 🔴 An unresolvable host is served the DEFAULT store's shop
- Status: Open
- Owner: Platform owner
- Source: observed live 2026-08-11 on `beautyinu.co`
- Statement: A host that does not resolve to a store shall be refused, never answered with another merchant's shop.
- Done when: a host with no matching store returns 404, the `STORE_SLUG` fallback applies only to localhost / bare IP / the base domain, and a test covers a public hostname falling through.

### 🔴 OBSERVED, NOT THEORISED
I added a Traefik router for `beautyinu.co` while its `store_domains` row was still `verifying`.
`https://beautyinu.co` answered **200 with `<title>Belanja Online - Batik Nusantara</title>`** — one
merchant's domain serving **another merchant's catalogue**. The router was removed within minutes and
the host is back to 503.

### Why
`getStoreByHost` builds candidates from three resolvers, and for `beautyinu.co` **all three return
null**:
- `slugFromCustomDomain` requires `status='active'` — correctly refuses a `verifying` row.
- `slugFromBaseDomain` only matches `*.tokophi.id`.
- `slugFromFirstLabel` **only handles `.sslip.io`** (`if (!host.endsWith(".sslip.io")) return null`).

With `candidates.length === 0`, the guard that says *"The host NAMED a store … → 404. Never silently
fall back to another merchant's storefront on someone else's hostname"* is **skipped** — it only fires
when candidates exist. Execution reaches:
```ts
const fallback = env("STORE_SLUG") || env("DEFAULT_STORE_SLUG");
return fallback ? await getStoreBySlug(fallback) : null;
```
`STORE_SLUG=batik-nusantara` in production. **The comment above it names the intended cases —
`localhost:4327`, bare IP, plain `tokophi.com` — but nothing checks for them.** It applies to every
host that fails to parse.

### Not currently exploitable, and that is precisely the danger
Traefik only routes `*.tokophi.com` / `*.tokophi.id` today, so an arbitrary host is refused at the proxy
before it reaches the app. ⚠️ **The exposure appears the moment a custom-domain router exists** — which
is the very next step of DOM-2. Anyone completing DOM-2 without this fix reproduces exactly what I saw.

### The fix
Gate the fallback on the host actually being a *no-name* host: `localhost`, a bare IP, `*.sslip.io`, or
the configured base domain apex. Anything else ⇒ `null` ⇒ 404. Make it a **pure predicate** in its own
module (the pattern that worked for `themeSourceStoreId`, `servableVerdict`, `isPubliclyServable`) so it
is testable without a database, and mutation-test it.

⚠️ **Order matters when finishing DOM-2:** flip `store_domains.status` to `active` **before** adding the
router, never after. I did it in the wrong order and served the wrong shop for a few minutes.

### State of the two waiting domains
`beautyinu.co` + `www` are **`active` at Cloudflare with live SSL** — DNS is finally correct
(`www` CNAMEs to `cname.tokophi.cc`). Our rows still read `verifying` / `error`
("Aktivasi custom domain belum dikonfigurasi oleh platform"), because the Cloudflare-SaaS automation
shipped in `804e6a4` has **no credentials configured in Coolify**. `taniniaga.com` + `www` are
`pending` behind the same gap. A prepared router file is parked at
`/root/tokophi-custom-domains.yaml.hold` on the VPS — **do not restore it until SEC-6 is fixed.**
