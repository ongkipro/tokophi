## ① N14 — every store's homepage ships THREE `<h1>`s · **S** · start here

`Hero.astro` renders the heading **inside the slide loop**, so a 3-slide carousel emits three `<h1>`s.
Confirmed on production (`curl -s https://toko.tokophi.com/ | grep -c '<h1'` → **3**).

Why it is first: it is small, it is on the page that matters most, and it is the other half of the
floor that just shipped — `index.astro` deliberately does not fire when a hero exists, so the page
either has no `<h1>` (fixed) or too many (this).

⚠️ **The non-first slides are `inert` + `opacity-0`, NOT `hidden`** — `inert` removes them from the
a11y tree for interaction, but the headings are still real elements in the document outline, and the
cross-fade (`grid-cols-1 grid-rows-1`, both slides stacked in one cell) is exactly why they cannot
simply be unmounted. Whatever shape the fix takes, the fade must survive.

Two shapes worth weighing before writing anything:
- one `<h1>` hoisted out of the loop, slides carrying `<p>`/`<span>` — simplest outline, but the
  heading then cannot change per slide, which is half of what a hero carousel is for;
- `<h1>` on slide 0 and `<h2>` (or `<p role="heading">`) on the rest — keeps the per-slide copy,
  costs a heading level that is arguably honest anyway.

- [ ] Decide the shape (say which, and why, in the commit body).
- [ ] Implement in `apps/storefront/src/components/sections/Hero.astro`.
- [ ] Extend `sections/h1-floor.test.ts` to pin the **count**, not just the emitter.
- [ ] **AC:** exactly one `<h1>` in the SSR response for a multi-slide hero — checked over HTTP against
      a real build, not by reading the template. The seeded demo store has 3 slides, so it is the case.
- [ ] Re-check the floor still works: template with no hero ⇒ still exactly one `<h1>`.

## ② N5 — `dom-size` 992 elements, scoring 0 · **M** · the only performance item left with evidence

After the last session's 8 runs this is not one candidate among several, it is **the** candidate:

```
mainthread-work-breakdown  3,4 s      ← style + layout
bootup-time                0,5 s      ← script. There is barely any.
scripts on the page        2, both Cloudflare's, neither ours
unused-javascript          0 bytes (passes)
legacy-javascript          0 bytes (passes)
```

The homepage ships every carousel slide and every section server-side. Candidates named in `NEXT.md`:
render only slide 1 server-side and hydrate the rest, or cut how many sections the default homepage
template seeds with.

🔴 **`SectionRenderer` must keep switching on every type.** Narrowing the palette stops merchants
adding more; deleting a branch **silently deletes published work** from templates saved earlier
(AGENTS.md, Store Builder). Narrow the palette, never the renderer.

⚠️ **The seed is not a migration.** Changing how many sections the default template seeds with reaches
**new stores only** — production keeps what it was given the first time. If existing stores need it
too, that is a data fix, and it must be stated in the commit body because nothing else will apply it.

- [ ] Measure first: which subtree is the 992? (Lighthouse `dom-size` details name the deepest and the
      widest element — read them before assuming it is the carousel.)
- [ ] Pick ONE change and measure it alone. Two at once and neither is attributable.
- [ ] **AC:** ≥5 mobile runs, report **median and range** (a single run means nothing here — measured
      spread on this page is 82–95). State the element count before and after.
- [ ] Confirm no merchant-visible section stopped rendering: build a template holding one of each
      section type and diff the rendered output before/after.
