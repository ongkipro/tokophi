# Database screening — production/local parity and integrity

**Status:** ready · **Size:** M · **Owner approval required before any production write**

## Objective

Produce an evidence-backed comparison of the local development database and the Vultr production
database. The screen must distinguish schema drift, migration drift, integrity defects, tenant
isolation gaps, business-data anomalies, and capacity risks. It must not copy production data or
credentials into the report.

## Safety boundary

- Default to read-only SQL with `default_transaction_read_only = on` and a bounded
  `statement_timeout`.
- Do not run migrations, seeders, cleanup SQL, `VACUUM FULL`, `REINDEX`, restore commands, or data
  fixes as part of the screen.
- Do not print connection strings, secrets, password hashes, tokens, customer addresses, phone
  numbers, or raw order payloads. Report aggregates and identifiers only where needed.
- `verify-ledger` opens a rollback-only write transaction to prove foreign-key enforcement. Treat it
  as a separate production action and obtain explicit approval before running it.
- Resolve Coolify containers by prefix, never by the deploy-specific full container name.

## Screening matrix

1. **Runtime identity** — record local Git HEAD, production image tag/ID, Postgres version, database
   size, and the newest applied Drizzle stamp.
2. **Migration parity** — compare the repository journal with `drizzle.__drizzle_migrations`; flag
   missing, skipped, duplicate, or future-stamped entries.
3. **Schema parity** — compare tables, columns, enums, defaults, constraints, indexes, foreign keys,
   extensions, RLS enablement, policies, roles, and grants.
4. **Tenant isolation** — aggregate missing/unknown `store_id` values, cross-store references, tables
   without the expected tenant policy, and owner-connection paths that depend only on application
   predicates.
5. **Commerce integrity** — screen orders, payments, line items, inventory movements, ledger entries,
   payouts, discounts, flash sales, media, and template assignments for orphans, impossible states,
   duplicate business identifiers, negative stock, and mismatched totals.
6. **Seed/config drift** — compare existing-store configuration with current seed intent for shipping
   methods, navigation, reviews, payment channels, payout configuration, and Store Builder defaults.
   Differences are findings, not automatic repair instructions.
7. **Capacity and maintenance** — rank table/index sizes, estimate dead tuples and index waste, confirm
   backup recency/size, and record disk headroom. Do not perform maintenance during screening.

## Deliverables

- A dated report under `specs/docs/tasks/` containing a local/production matrix, SQL evidence,
  severity, business impact, and a proposed owner for every finding.
- A reusable read-only SQL script under `ops/` with explicit transaction and timeout guards.
- Separate remediation tasks for each confirmed defect. No cleanup or migration is bundled into the
  screening task.

## Acceptance criteria

- Every check runs against both local and production, or the report states why one side could not be
  checked.
- Production queries leave no committed writes and disclose no secrets or customer PII.
- Migration journal, applied stamps, schema/RLS, ledger/order/payment integrity, seed drift, backup
  recency, and database/disk size all have an explicit result.
- Counts are generated by queries and timestamped; none are copied from an older status document.
- Any proposed destructive repair has its own approval-gated runbook with a dry-run and rollback
  path.
