## ② security/super-admin — every store we provisioned got the owner password `tokophi123`

🔴 **The blocking finding of the wave.** `apps/super-admin/lib/actions.ts:27,107` hashed the new owner's
password from the `DEV_PASSWORD` constant — a string published in this repository and in `AGENTS.md`.

Onboard `budi@tokosaya.com` and anyone who knows that email address logs in at `app.tokophi.com` as store
**owner**: every order with the buyer's name, WhatsApp and full delivery address, every customer record,
and through `settings:write` the bank account and `requestPayout`.

`AGENTS.md` already carried the rule — *"Never mint a fixed password. Random per invite, revealed once"* —
and `invitePlatformAdmin`, **250 lines below in the same file**, was already fixed, with a comment
asserting the other paths were correct. They were not. **Instance patched, class missed.**

`createStore` now mints `tempPassword()` and returns it; `toko-client` reveals it once in a persistent
toast. A toast and not a dialog: the handler `router.push`es to `/toko/{id}` immediately and a dialog
would unmount, while `<Toaster>` lives in the root layout and survives the navigation. An action that
returns a password the UI drops on the floor leaves the merchant unable to log in at all.

Proven on `tokophi_test`, rolled back: `verify('tokophi123') = false`, `verify(minted) = true`.
`no-fixed-password.test.ts` guards the **class** — it fails if any `hashPassword()` call in `actions.ts`
receives anything but a freshly minted value, if a minting action fails to hand it back, or if any write
is anchored to a frozen date. Proven red (3 of 5) before green.

**Also removed: the frozen `ANCHOR`.** `createStore` stamped `accounts.created_at`, `stores.created_at`,
`store_users.accepted_at` and `store_stats.updated_at` with `2026-07-02` while computing `trialEndsAt`
from the real clock — one row, two clocks. **A store was born ~30 days old with a 3-day trial and dropped
out of `newSignups30d` permanently on its first day.** All four columns are `defaultNow()` now, and the
trial length reads `BILLING.TRIAL_DAYS`, matching `provision.ts`.

Two stale UI strings fixed alongside: both dialogs told the operator the password would be `tokophi123`.
The invite one had been false since `invitePlatformAdmin` was fixed.

🔴 **NOT fixed, and it is now the most visible half of this defect:** `apps/super-admin/app/login/page.tsx`

## ③ fix/admin — twelve frozen "today" anchors, one of which rewrote data on every save

The seed may be anchored to `2026-06-30`. The app is not. `AGENTS.md` records this class **twice
already** — the discount editor's `ADMIN_TODAY` made every voucher a merchant created born already
expired, and the super-admin healthcheck read a live store as −23 hari. Twelve more were still live.

**The write.** `actions/articles.ts` stamped `publishedAt = 2026-06-30`, and because `fields()` is a full
replace, **re-saving an already-published article walked its date backwards** — the same mechanic as the
voucher bug, one file over. `updateArticle` now reads the row's current `publishedAt` inside `withTenant`
first, and that read doubles as the tenant check: a foreign id returns nothing and the update is skipped,
mirroring `updateDiscount`. The rule is extracted to `lib/publish-date.ts` because a `"use server"` module
can only export async actions, so it could not otherwise be tested.

Proven against real Postgres, rolled back:

```
OLD  three saves of an article truly published 2026-07-20 08:30
     -> 2026-06-30 every time                      moved_backwards = t
NEW  three saves -> 2026-07-20 08:30 unchanged     moved_backwards = f
     first publish of a draft -> today (was 2026-06-30, already past)
```

**The reads (ten).** A follow-up due today computed +32, so the CRM overdue filter `dueDays <= 0` could
not fire for it; customer-detail rendered "Pelanggan sejak −32 hari lalu"; the whole Seller activity feed
read "0 menit lalu", because `Math.max(0, ANCHOR - d)` clamped every event dated after the anchor.
`lib/mock/store.ts` and every `packages/db/src/seed*.ts` anchor are left frozen deliberately.

Also: `markLabelsPrinted`'s caller toasted `printedNumbers.length` instead of the `.done` the action
returns from `.returning()` — the action was fixed in `#117` and its caller was not. The copy now

## ④ fix/orders — the sixth default-location copy, on the one connection with no RLS

`#127` routed five copies through `lib/inventory-location.ts` and left this one:
`apps/admin/app/api/public/order/route.ts` defined its own `defaultLocationRow(variantId)` with **no
`store_id` predicate at all**. It is the worst of the six — the route has no session, runs on the
**OWNER connection with RLS off**, and `inventory_levels` has no `store_id`, so the `locations` join
**picks** a row without proving whose. `order by loc.is_default desc` will prefer another store's default
warehouse.

Now routed through `defaultInventoryLevelId(db, variantId, store.id)`, using the id the route already
resolves from `stores.slug`. `#127`'s contract says a `null` return is **ambiguous** — "not stocked yet"
and "not ours" are indistinguishable to the query — so each of the three sites handles it by what it is:

| site | kind | on `null` |
|---|---|---|
| pre-check | READ | `available 0` → refuse. Both readings mean the same thing where the only outcome is a refusal, and ownership is proved separately: the variant's product was read with `eq(products.storeId, store.id)` just above |
| `FOR UPDATE` | GUARD in front of a write | **REFUSED, not skipped** (`throw OutOfStock`) — identical to the old missing-row branch. Skipping would sell stock we cannot prove we have |
| decrement | UNGUARDED write | resolves nothing now: the lock loop records `inventory_levels.id` in a spend map and the write targets that id, so check and write are the same **ROW**, not the same expression re-evaluated. Stronger than before |

Verified in `tokophi_test`, rolled back: store A's variant stocked at A's default location resolves for A
and returns `null` for B, while the old unscoped subselect handed A's row to a caller that named no store.

⚠️ **Correction to `#127`'s framing, worth keeping.** `NEXT.md` said seven copies across four files and
that "only the last one carries the tenant filter". There were **eight**, and the claim is false —
`products.ts:91` and `:135` carry it too, and the four join-based admin copies run inside `withTenant`
where `locations` is RLS'd. The genuinely exposed sites were **2**: `order-status.ts` (reached by
`ka-tracking.ts` on the owner connection) and this public order route. Treat it as a duplication task
with two real security sites, not seven.

**Also: `desc()` in drizzle emits a bare `DESC`, which is NULLS FIRST in Postgres.**
`data/order-detail.ts:306` ordered payments with `desc(payments.paidAt)` while `data/orders.ts:234` used
`paid_at desc nulls last`. **Both files carried comments asserting they matched** — the detail one reads
*"Must match the LIST's definition exactly … unpaid last … One order, one answer."* On an order with one
unpaid and one paid payment the two screens name **different payment methods for the same order**. One
exported `latestPaymentFirst()` now serves both, with a real-Postgres test proven red then green.

**Latent, not live:** 827 payments, 46 with `paid_at IS NULL`, and **0 orders** currently carry both
shapes. This item was listed under "✅ Closed this session — do not redo" in `NEXT.md`; it was not closed.

⚠️ **It is NOT a money bug**, and an earlier draft of the audit said it was. Both data files' comments
claim this ordering feeds `createShipment`'s courier cash-collection instruction. It does not:
`apps/admin/lib/actions/shipping.ts:512` derives COD independently via
`exists (select 1 from payments p where p.order_id = … and p.method = 'cod')` — an existence test no
`ORDER BY` can affect. The comments now say so. Note what that means: **the same two files have now been
found carrying two false comments each.**

*Same class, lower stakes and **not fixed**:* `data/articles.ts:57` sorts every draft above every
published post in the seller's Blog list. Carried into `NEXT.md`.

## ⑤ test — 22 money tests that had never run on anyone's machine

`apps/admin/lib/ledger-credit.test.ts` skips without `TEST_DATABASE_URL`. It guards the claims only a
database can settle — that a double-credit is impossible (three partial unique indexes), and
`select sum(…) for update`, which Postgres rejects outright and which `tsc` cannot see inside a SQL
string. It ran only if a developer happened to export that variable by hand. Nobody did, and there is no
CI here, so **22 tests over the code that decides when a sale becomes withdrawable had never run**.

The skip was deliberate and well-meant — it kept `vitest run` green on a laptop with no test DB. The cost
was silence.

`test/db-setup.ts` (a vitest `globalSetup`) derives `<DATABASE_URL>_test`, creates that database if
absent, migrates it to head and exports `TEST_DATABASE_URL`. The container is already required to run the
app, so the suites simply run:

```
before   16 files passed, 1 skipped   145 passed, 22 skipped
after    22 files passed              182 passed,  0 skipped
```

**THE GUARD IS THE POINT:** the resolved name **must** end in `_test` or setup throws. These suites seed
stores, orders and payments; they roll every transaction back, but pointing them at the shared dev
database must stay impossible. **Do not relax it.**

An unreachable database still SKIPS — with a banner naming the reason and the command to fix it — so a
machine without Docker gets a green run instead of a wall of noise. `npm run test:db` turns that skip into
a failure; use it before a PR. An explicit `TEST_DATABASE_URL` still wins.

Verified: the guard refuses a non-`_test` name; an unreachable host skips loudly under `npm test` and
fails hard under `npm run test:db`; a database that does not exist yet is created and migrated (86
migrations, 22 tests green) then dropped.

## ⑥ storefront/seo — the `<h1>` count was wrong in BOTH directions, and a third case fell between them

**N14 — `Hero.astro` emitted one `<h1>` per slide.** `#127` fixed only the *missing*-`<h1>` case (a
builder homepage with no Hero rendered **zero**); a homepage *with* a Hero rendered **three**, because the
heading sat inside the slide loop. One slide renders as `<h1>` now; the rest are a `<p>` sharing **one**
heading-class constant, so the two tags stay pixel-identical. The cross-fade is untouched — nothing is
unmounted, nothing in the carousel script selects `h1` (it drives `[data-hero-copy]`), and off-screen
slides are `inert` either way; both were checked before being relied on.

Shape chosen deliberately: a single hoisted `<h1>` was rejected because the heading could then not change
per slide, which is half of what a hero carousel is for; `<h2>` on the rest was rejected because they are
not sub-sections of slide 1, they are the same banner in another state.

🔴 **A THIRD defect was live *between* the two fixes, and this is the part to remember.** `#127`'s floor
keys on `content.some(s => s.type === "hero")`, but `heroSlides()` deliberately keeps a slide that has an
`imageUrl` and **no heading** — a pictorial hero. On that template the floor **stood down** *and* the hero
shipped `<h1></h1>` itself: measured on `dd2129d`, **two empty `<h1>` and no real heading on the page**.
So it is `HEADING_INDEX`, not slide 0, and the floor now goes through `heroSlides()` too. **Both halves
ask the same question** — "is there a slide whose heading is non-blank" — so they are two halves of one
predicate instead of two predicates that can disagree. ⚠️ **CONTRACT:** change one and they silently
disagree — zero `<h1>` on a pictorial hero, or two on an ordinary one, with build, lint and `astro check`
green either way. `h1-floor.test.ts` had pinned the old predicate verbatim and was updated with it.

Measured over HTTP against a real build, three homepages:

| template | on `dd2129d` | after |
|---|---|---|
| hero, 3 slides | 3 | **1** (+ 2 `<p>`) |
| hero-less | 1 | **1** — the `sr-only` floor, carrying the store name from the DB |
| heading-less (pictorial) hero | **2, both empty** | **1** — the floor, correctly firing |

`SectionRenderer` untouched — it still switches on all 14 types, so nothing published can stop rendering.

**PDP gallery thumbnails had no `srcset` at all** — found by the measurement stream, on no task list. The
`<button data-thumb>` carried a full `data-srcset` ladder all along (it promotes it onto the main image on
click) while the visible `<img>` **inside** it rendered a bare `src` into a 66 px box. Same family as
`#119`/`#120`: markup valid, `astro check` green, bytes wrong. Measured on `/produk/dress-midi-bunga` at
412×915, 3 runs each, byte-identical every run:

| | before | after | delta |
|---|---|---|---|
| DPR 1 | 153 940 B | 30 782 B | **−80,0 %** |
| DPR 2 | 151 552 B | 42 646 B | **−71,9 %** |

The `sizes` derivation is the part to keep: it comes from container padding + `gap-3` + **the thumbnail
COUNT**, not from the `max-w-[7rem]` class. `max-w` only *caps* a `flex-1 basis-0` tile and the measured
box is **66 px** at n=5 on a 412 px phone — declaring the cap over-claims 1,7× and costs a whole rung:
`sizes="112px"` pulls the 400 w files for **60 114 B** where the derived value pulls the 200 w files for
**42 646 B**. **17 468 B for one word.**

**The upload width ladder never offered the original.** `WIDTHS` in `data/catalog.ts` and the allow-list in
`apps/admin/app/api/uploads/[name]/route.ts` are **one decision in two files**, and both stopped at 1200
while `saveImage` caps an upload at `MAX_DIM = 2000`. An out-of-list width 400s, so 1200 was a hard
ceiling: a `sizes="100vw"` merchant hero on a 1920 px desktop got a 1200 px file stretched, with the
2000 px original unreachable on disk. Both now end at 2000.

⚠️ **The never-upscale guard was verified two ways, because "we checked the guard is load-bearing" is
exactly the kind of claim this repo keeps finding to be false.** Calling the route handler directly,
`?w=1200/1600/2000` on a 300 px source all return the original **byte-for-byte**; and running the same
sharp pipeline **with the guard removed** enlarges 300 → 2000 px, which proves the guard is what stops it
and not `sharp`. `?w=2400` / `?w=999` / `?w=1` still 400, so the allow-list still bounds the cache key
space at original + 6 widths.

**Two browser checks, both repaired after being caught flaky.** A coin-flip red check is how `verify-rls`
sat red for weeks while two cross-tenant leaks shipped past it:

- `check-pdp-srcset.mjs` failed **5 runs in 6** against a correct build. The spec lets Chromium satisfy the
  66 px thumbnail out of the main photo's already-fetched 800 w copy, and the naive `currentSrc` reading
  called that *cheaper* outcome a 6.1× regression — **zero extra bytes were transferred**. It now measures
  on a second, **isolated** selection, every candidate URL rewritten unique per `<img>`.
- `check-h1-floor.mjs` writes to the shared dev database — it stages a `page_templates` row for a store
  that has none. It used a **fixed UUID** and a `finally` block, so two agents running it at once deleted
  each other's row mid-poll. It now uses a random id per run **plus a Postgres session advisory lock on a
  reserved connection**: a session lock is released when the connection dies, and a `finally` block is not.

**Both `<h1>` alarms are kept on purpose, and they are not redundant.** `sections/h1-floor.test.ts` pins
the **premise** — that `Hero` is still the only section emitting an `<h1>`, and that both halves still key
on the heading text — with no DB and no browser, which is the only thing that can see it.
`scripts/check-h1-floor.mjs` pins the **rendered count** against templates that live in the database,
which no unit test can reach.

**Left open deliberately, and the reasoning is worth adopting as policy:** `Header.astro` still has bare
`<img>` sites which render on **every page**, in a different file with separate `sizes` derivations.
`check-pdp-srcset.mjs` **prints** them (10 catalog images with no `srcset`) without failing — *a check red
for work nobody in this change can land is a check everyone learns to ignore.* Tracked in `NEXT.md`.

## Two gates that only fire if you run them

Demonstrated three separate times this session, and it is the single most reusable thing here:

- **`next build` does not run ESLint.** ESLint was the only gate that caught a backtick inside a JS
  template literal that had silently terminated a SQL string.
- **ESLint and `next build` do not typecheck test files.** `tsc --noEmit` was the only gate that caught a
  non-overlapping type assertion in a newly added test.
- **All of them are green on live outages** — this repo's own history: a `ReferenceError` inside a client
  `<script>`, and `select sum(…) for update` inside a SQL string.

Run all three plus the browser checks before any PR. Nothing runs ESLint automatically, which is how it
rotted to 19 errors.

### One number did not match the local measurement, and the reason is worth keeping

The homepage lost only **232 B** where the local build measured **−2 940 B**. Not a regression, and not
noise: the widened upload ladder adds two `srcset` candidates to each of the **11** upload-backed images
on that page — 22 × ~76 B ≈ **1 672 B** of new HTML — which offsets most of what `Stars.astro` saved.
The local page had no upload-backed images, so it never paid that cost.

**The element count, which was the actual target, matched exactly: 1068 → 960 = −108**, the same delta
measured locally (1023 → 915). It is a deliberate trade — HTML bytes spent to buy image bytes, and image
bytes are the larger number by two orders of magnitude.
