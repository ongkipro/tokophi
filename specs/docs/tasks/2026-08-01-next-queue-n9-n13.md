## N9 — the default-location expression, and the tenant filter four of its five copies never had

**This was not a refactor. Four of the five copies were missing the tenant boundary**, and NEXT.md
described it as a tidy-up ("only the last one carries the tenant filter"). Measured on `origin/main`:

```
apps/admin/lib/actions/purchases.ts   2 copies   0 × locations.storeId
apps/admin/lib/actions/inventory.ts   1 copy     0 × locations.storeId
apps/admin/lib/actions/products.ts    3 copies   0 × locations.storeId
apps/admin/lib/order-status.ts        1 copy     (raw SQL — the only one with `loc.store_id = …`)
```

`inventory_levels` has no `store_id`, so RLS cannot scope it (AGENTS.md, THE CHILD-TABLE RULE). The
`locations` join **picks** a row; it does not prove whose row it is, and `order by is_default desc`
will happily prefer another store's default warehouse. So a `variantId` that belongs to somebody else —
a PO line, a bulk stock save — resolved to **their** shelf and the write landed there, silently.

Now **one** helper, `apps/admin/lib/inventory-location.ts`:

- `defaultLocationId(db, storeId)` — where a NEW inventory row is created.
- `defaultInventoryLevelId(db, variantId, storeId)` — the variant's existing row at that location.

`storeId` is a **required parameter**, not something read from a session, because one call path
(`order-status.ts` ← `ka-tracking.ts`, the courier webhook) runs on the **owner connection** with RLS
off entirely and has no session to read.

⚠️ `defaultInventoryLevelId` returning `null` is **ambiguous** — "not stocked yet" and "not ours" look
identical to the query. It must be a SKIP unless the caller has separately proved ownership.
`updateProduct` is the one caller that inserts on `null`, and it is allowed to: it reads the parent
product under RLS and bails before touching any child.

**Guard:** `apps/admin/lib/inventory-location.test.ts` — scans the admin tree and fails if the
expression is written anywhere but the helper (both the Drizzle form and the raw-SQL form). Verified
it flags the pre-change tree: 3 + 2 + 1 + 2 matches across the four files above. A sixth copy
type-checks and passes everything else, which is precisely why the guard is a source scan.

## N10 — `deleteLanding` reported success over a delete that matched nothing

The remaining gap: it returned `Promise<void>`, so the editor toasted **"Landing dihapus"** and
navigated to `/promo` regardless. A DELETE matching zero rows is **not an error** — an id belonging to
another store is filtered out by RLS in silence, and so is a second click on a stale tab.

`.returning()` now decides, and the caller reads it (`landing-editor-client.tsx`, same commit — this
is the two-file change AGENTS.md warns about; converting the action alone would have been worse than
the bug).

## N11 — a builder homepage with no Hero rendered zero `<h1>`

`Hero` is the **only** section in the registry that emits an `<h1>` (verified: every other section
starts at `<h2>`; Multicolumn's `<h1>` is inside a comment). A merchant who builds a homepage without
dragging a Hero onto it therefore shipped the shop's most important page with no top-level heading —
nothing for a screen reader's outline, nothing for a crawler to read as the subject.

`index.astro` now renders `<h1 class="sr-only">{store.name}</h1>` when the template holds no `hero`.
Hidden, not visible: the merchant designed that page, and injecting a headline they did not write is
the same offence the fallback-hero comment already refuses to commit.

**Exercised, not just built** — against the real DB, with the row snapshotted and restored:

| template | `<h1>` count | what |
|---|---|---|
| as seeded (hero first) | 3 | the hero's, one **per slide** — a pre-existing defect, see below |
| hero removed | 1 | `<h1 class="sr-only">Batik Nusantara</h1>` |

The template row was restored byte-for-byte and re-verified (`diff` clean, 9 sections, `hero` first).

⚠️ **Found while measuring, NOT fixed:** `Hero.astro` emits one `<h1>` **per slide**, so the seeded
3-slide carousel publishes **three `<h1>`s** on every store's homepage. The floor deliberately does not
fire when a hero is present, so it neither causes nor worsens this — but it is real and it is on the
one page that matters most. Added to the queue.

**Guard:** `apps/storefront/src/components/sections/h1-floor.test.ts` pins the premise — if any other
section starts emitting an `<h1>`, the condition is wrong in the expensive direction (two `<h1>`s) and
the test says so. Nothing else can see this: the template is merchant data, so a build renders whatever
the demo store happens to have saved.

## N13 — `<lastmod>` where the data supports it, and a written reason where it does not

`pages.updated_at` exists **and is genuinely maintained**: `actions/pages.ts` sets it from one shared
`fields()` used by create *and* update, so every save moves it. `/halaman/*` now carries `<lastmod>`.

Products and categories **cannot**, and the sitemap now says why in the file: the only date available
for them is one that never moves after insert, and Google's documented response to an unreliable
`<lastmod>` is to distrust the field for the **whole document** — which would cost the blog and pages
entries the real signal they do have.

Verified against production data, served from a real build:

```
55 URLs · 21 with <lastmod>  =  15 blog + 6 halaman   (0 products, 0 categories — deliberate)
```

**To finish N13 properly** somebody has to decide on `products.updated_at` (+ `collections`): an
idempotent migration, plus every write path that must touch it. That is an `M`, it lands in
`packages/db`, and it collides with whatever else is generating a migration — check
`origin/main:packages/db/drizzle/meta/_journal.json` first.

### 🔴 N7 is reversed — do not remove the `scroll` trigger

The queue's reasoning: the score is bimodal because Lighthouse scrolls, `scroll` is a pixel load
trigger, so some runs pay for all three vendor bundles. Removing `scroll` was offered as the fix, at
the cost of losing the reader who scrolls and never taps.

**In all three runs the bimodality appeared and no vendor bundle loaded at all.** The only two scripts
on the page were Cloudflare's own (`email-decode.min.js`, `beacon.min.js`). So that change would pay a
real tracking cost and buy nothing. What is left is our own main thread — `mainthread-work-breakdown`
**3,4 s** against `bootup-time` 0,5 s, over a **992-element DOM**: style and layout, not script.

### ✅ N6 is closed — not reproducible, and its suggested cause was impossible

`unused-javascript` and `legacy-javascript` both **pass with 0 bytes** in all 8 runs. And the advice
("check the Vite `build.target`") assumes a bundle that does not exist: `dist/client/_astro/` holds one
CSS file and **zero `.js`**. Most likely the 44/12 KiB were measured before `#122` deferred the pixels
— i.e. they were the vendors' bundles.

### N4 — the 7,1 s speed-index does not reproduce

Mobile SI **median 4,1 s against LCP 2,8 s** (a ~1,3 s gap, not 5,4 s); on desktop it does not appear
at all (SI median 0,5 s). Still open, still worth the filmstrip, but re-sized.

### N2 — re-confirmed still undone

The homepage serves 2 `/cdn-cgi/l/email-protection` links and `email-decode.min.js` loads in every
single run. The zone setting has not been changed.

**Net effect on the queue:** N5 is now the only performance item with evidence behind it.
