## ③ 🔴 The finding: pointing all three services at `tokophi_app` takes the product down

The preflight's step 2 is *"set `APP_DATABASE_URL` for `admin`, `super-admin`, `storefront`, pointing
at `tokophi_app`"*. Measured, that is an outage, not a hardening step:

- **All 50 policies are `TO PUBLIC`** (`grep -c "TO " ` over every `CREATE POLICY` in
  `packages/db/drizzle/*.sql` → **0** of 50 name a role). They therefore apply to *any* role without
  BYPASSRLS — including a connection that simply **is** `tokophi_app`.
- With no `app.store_id` GUC set, `app_current_store_id()` returns NULL, so `store_id = NULL` is NULL,
  so **every one of the 53 policed tables returns zero rows**.
- The surfaces that read **outside** `withTenant()` are exactly the ones that would go blind:
  `apps/super-admin` (cross-tenant by definition), `apps/storefront` (Host-resolved catalog),
  `apps/admin/lib/auth.ts` (reads `store_users` *before* a session exists — nobody could log in),
  `apps/admin/app/api/public/**`, the cron sweeps and `lib/provision.ts`.
- This is not a new opinion. `0058_*.sql`'s own header enumerates those readers and says they run as
  owner; `specs/docs/SECURITY.md` §4 records it as a **decision**; `.env.coolify.example` says in as
  many words *"Do NOT wire the canonical admin service to this until owner-only routes
  (`/api/public/*`, cron, cross-tenant reads) are split onto a second pool."*

So `DATABASE_RUNTIME_ROLE: app` on those three services is a **label the code has never been able to
honour**, which is precisely why Task 2.1 was recorded as *"changed labels but did not prove a
restricted runtime"*. A real restricted runtime needs **two pools** — owner for the pre-session and
cross-tenant paths, restricted for tenant data. That is what shipped here; see ③b.

**Independently re-measured by the coordinator, same day, same numbers** (`stores` 0, `store_users` 0,
`products` 0 as `tokophi_app` with no GUC, against owner's 14 / 13 / 78). The credential was also
provisioned in that window: `tokophi_app` now has `rolcanlogin = t` and a password, still
`rolsuper = f`, `rolbypassrls = f`. The secret lives root-only on the VPS and appears in no file here.

## ③b The chosen shape — (b), two named pools, with the labels corrected as a consequence

Two shapes were on the table. **Shape (b) shipped**, because shape (a) alone is not implementable:
labelling `admin` app-role does nothing about the fact that its OWN pre-session auth read, its public
API and its cron sweeps have no tenant to scope by, and there are **34 files** in `apps/admin` holding
the `db` handle, not one.

| handle | pool | who calls it |
|---|---|---|
| `db` | owner (`DATABASE_URL`) — unchanged | the enumerated owner paths: `lib/auth.ts`'s pre-session `store_users` read, `apps/admin/app/api/public/**`, the cron sweeps, `lib/provision.ts`, super-admin, the storefront |
| **`appDb`** (new) | restricted (`APP_DATABASE_URL`) in app-role mode; the owner pool otherwise | **`withTenant()` and nothing else** — every merchant read and write, 79 files |

- **Why this is (b) and not a third thing:** `db` *is* the "explicit, named, greppable owner escape".
  Choosing it over `withTenant`/`withCurrentTenant` has been the deliberate, documented decision since
  day one (AGENTS.md: *"Do NOT use a bare module-level `db` for admin tenant data… Auth, super-admin
  and the storefront are the deliberate exceptions"*). Today both handles are the same connection,
  which is exactly why the convention could be true in prose and false in fact. This makes the
  existing boundary mechanical.
- **How admin's pre-session auth read still works:** it is on `db`, the owner pool, on purpose. That
  is the answer to the question shape (a) asks — and it generalises, because auth is not the only such
  path (public API, cron, `provision.ts` slug uniqueness).
- **Why super-admin and storefront are declared `owner`:** measured, **0** `withTenant` call sites in
  either (admin has 79). An app-role label there would require a credential that gates nothing and
  open a second pool nothing ever queries, while inviting exactly the outage in ③.
- **Cost:** an app-role admin holds up to 20 connections instead of 10, against `max_connections = 100`
  (10 open on production at the time of writing). The second pool is lazy — postgres.js opens nothing
  until the first query — so owner-mode surfaces pay zero.

**Consequence for this lane:** the fail-closed gate is built and armed; merchant traffic moves onto a
genuinely restricted connection; the two surfaces that cannot move say so in the file that configures
them. `APP_DATABASE_URL` on `admin` is now a hard deployment precondition (⑤).

## ⑤ Deployment precondition — READ BEFORE MERGING

**In this order. Step 2 before the merge, not after.**

| # | step | who | state |
|---|---|---|---|
| 1 | `ALTER ROLE tokophi_app WITH LOGIN PASSWORD '<generated>'` | owner | ✅ **done 2026-08-22** — verified `rolcanlogin = t`, `rolsuper = f`, `rolbypassrls = f` |
| 2 | Set **`APP_DATABASE_URL`** in Coolify **on the `admin` service only**, pointing at `tokophi_app` on `postgres:5432/tokophi` | owner | ⛔ **required before merge** |
| 3 | Merge, watch the deploy land (`app.tokophi.com` 503 → 200), then let the next lane merge | owner | after 2 |

- **Do NOT set `APP_DATABASE_URL` on super-admin or storefront.** They are declared `owner` and never
  read it; pointing them at the restricted role is the outage in ③.
- **`${APP_DATABASE_URL:?…}` fails the whole compose at parse time**, not just the admin container —
  that is the loud failure Task 0.1 chose for `AUTH_SECRET`/`POSTGRES_PASSWORD`, and it is why the
  variable has to exist first.
- **What a good deploy looks like in the admin log:** `[@tokophi/db] restricted database identity
  verified: tokophi_app`, once, at start. A bad one prints `[@tokophi/db] REFUSING TO SERVE — …` and
  the container exits 1 (then restarts, so it will be a visible crash loop, not a silent downgrade).
  Neither line ever contains a connection string.
- **Rollback** is one variable: set `DATABASE_RUNTIME_ROLE=owner` on admin (or revert this PR).
  Merchant traffic then runs on the owner pool with `SET LOCAL ROLE` enforcing, exactly as it does
  today.

## ⑥ Test-database side effects

The Postgres half of `db-identity.test.ts` creates a **cluster-global** role named
`t412_probe_<random>` with a randomly generated password, uses it against the `*_test` database only,
and `DROP ROLE`s it in `afterAll` (with `drop owned by` first, or the drop fails). Roles are
cluster-wide, so this is visible from the shared dev database's cluster while a run is in flight —
it is additive, it is dropped, and it never touches the shared dev DB's data.

⚠️ A throwaway script (`live-app-role.ts`, in a scratchpad, **not committed**) drove app-role mode end
to end and leaked ONE role on its failure path: the fail-closed `process.exit(1)` fires from the
module-load handler, so the script's `finally` never ran. `t412_live_78da92` was dropped by hand and
verified gone; the shared dev DB was checked and holds no `t412%` store. **If you write a script that
exercises the refusal path, drop its role afterwards — the exit is the point, and it takes your
cleanup with it.**
