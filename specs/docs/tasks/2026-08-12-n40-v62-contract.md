## 1. What the docs say vs what the code sends vs what the sandbox is

`kaCreateOrder` (`packages/lib/src/kiriminaja.ts:149`) books on `v6.1/request_pickup` today.
The v6.2 doc contradicts itself on the destination field names:

| Source | Destination fields it claims |
|---|---|
| v6.2 doc **table** | `destination_province_id` · `destination_county_id` · `destination_subdistrict_id` (required) · `destination_village_id` |
| v6.2 doc **request example** | `destination_provinsi_id` · `destination_kabupaten_id` · `destination_kecamatan_id` — no village field at all |
| v6.2 doc **error example** | `"The destination kecamatan id field is required."` (names `destination_kecamatan_id`) |
| **v6.1** doc + our working code | `destination_kecamatan_id` · `destination_kelurahan_id` |
| **SANDBOX (measured)** | **`destination_kecamatan_id` (int) · `destination_kelurahan_id` (int)** — identical to v6.1 |

**Every name unique to the v6.2 doc is wrong.** The table's English names do not exist; the
example's `destination_provinsi_id`/`destination_kabupaten_id` do not exist either (both are
silently ignored). The doc also **omits `destination_kelurahan_id` entirely** — but the struct has
it, and that is the village-level field migration 0042's snapshot exists to book with.

## 2. Evidence

All probes SANDBOX (`tdev.kiriminaja.com`), `KIRIMINAJA_ENV` unset. Key read from the app's own
env source, never printed. Probe script lived in the session scratchpad, not the repo.

### 2.1 The path exists

Unauthenticated `POST` (no key involved) distinguishes real routes from missing ones:

```
POST /api/mitra/v6.2/request_pickup → 401 {"method":"/api/mitra/v6.2/request_pickup","status":false,"text":"Unauthorized."}
POST /api/mitra/v6.3/request_pickup → 200 {"status":false,"text":"Unable to find your endpoint target","endpoint":"request_pickup"}
```

A real route answers 401 and echoes its own path; a missing one answers "Unable to find your
endpoint target". So the v6.2 path is `/api/mitra/v6.2/request_pickup` — same shape as v6.1.

### 2.2 The smoking gun — the sandbox names its own struct fields

v6.2 is a **Go service** (v6.1 is not — it answers Laravel-style). Sending a candidate field with
the **wrong JSON type** makes Go's unmarshal name the struct field if it exists — and silently
ignore the field if it does not. Either way the request is unbookable. Measured:

```
destination_kecamatan_id:"abc"   → bind "packages.destination_kecamatan_id" … Go struct field
                                   RequestPickupV62RequestPackage.packages.destination_kecamatan_id of type int
destination_kelurahan_id:"abc"   → bind … destination_kelurahan_id of type int
destination_subdistrict_id:"abc" → (ignored) "Terjadi kesalahan dalam proces create package"
destination_village_id:"abc"     → (ignored) same
destination_province_id:"abc"    → (ignored) same
destination_county_id:"abc"      → (ignored) same
destination_provinsi_id:"abc"    → (ignored) same
destination_kabupaten_id:"abc"   → (ignored) same
```

The struct is literally named `RequestPickupV62RequestPackage` — this is the v6.2 handler, not a
fallback. **Only `destination_kecamatan_id` and `destination_kelurahan_id` exist.**

### 2.3 The full v6.2 request struct, bind-verified field by field

`RequestPickupV62Request` (top level): `address` string · `name` string · `phone` string ·
`zipcode` string · `kecamatan_id` int · `kelurahan_id` int · `latitude` float64 ·
`longitude` float64 · `platform_name` string · `schedule` string · **`payment_method` string** ·
**`pin` string** · `packages` [].

`RequestPickupV62RequestPackage`: `order_id` string · `destination_name` string ·
`destination_phone` string · `destination_address` string · `destination_kecamatan_id` int ·
`destination_kelurahan_id` int · `destination_zipcode` string · `weight` int · `width` int ·
`length` int · `height` int · `qty` int · `item_name` string · `item_value` int ·
`shipping_cost` int · `service` string · `service_type` string · `package_type_id` int ·
`insurance_amount` **int** (doc says "numeric") · `cod` int · `drop` bool · `note` string.

⚠️ **`add_cost` is NOT in the struct** — the doc's table lists it, the sandbox ignores it. We never
send it; do not start.

Every field `kaCreateOrder` sends today exists in v6.2 under the same name and type. The only
additions are `payment_method`, `pin` (KA Credit — we do not use it) and the doc-known `drop`.

### 2.4 Validation order on v6.2 (observed, sequential — first error wins)

1. JSON **bind** (types) → `bind "…" from body: json: cannot unmarshal …`
2. `address` length → `"Address minimal berisi 10 karakter."` (empty body dies here)
3. `order_id` prefix registration → `"Paket <id> : Format Order ID tidak sesuai dengan yang anda daftarkan."`
4. courier exists → `"Paket <id> : kurir tidak ditemukan"`
5. KA Credit PIN (only when `payment_method:"credit"`) → `"Unable to proceed, pin invalid"` + `data.error:"PIN_INVALID"`
6. `schedule` window → `"Jadwal penjemputan tidak lagi tersedia"`
7. create/destination resolution → `"Terjadi kesalahan dalam proces create package"` (generic)

⚠️ Two migration-relevant behaviour differences from v6.1, both in **error** responses:
- v6.1 answers business failures as **HTTP 200** `{status:false, method:"request_pickup", …}`;
  v6.2 answers **HTTP 400** with `{status:false, text}` and often **no `method` field**. Our `ka()`
  helper already parses JSON bodies regardless of HTTP status, and `kaCreateOrder` reads only
  `status`/`text` — so no code change needed, but do not add an HTTP-status check while migrating.
- A nonexistent destination id on v6.1 gets the specific *"Tujuan pengiriman … doesn't exists"* +
  `fail_package` echo; on v6.2 it gets the **generic create error**. The seller-facing message for a
  bad destination becomes less useful — nothing we can fix, worth knowing before someone files it
  as our bug.

## 4. Verdict: SAFE TO MIGRATE — it is the one-line bump N40 hoped for

The v6.2 contract **is** the v6.1 contract plus optional KA-Credit fields. No field renames, no
destination-name change, no payload restructuring. Minimal change set (do NOT do it in this branch):

1. **`packages/lib/src/kiriminaja.ts` → `kaCreateOrder()`** — the path string
   `"/api/mitra/v6.1/request_pickup"` → `"/api/mitra/v6.2/request_pickup"`. That is the migration.
2. **Same function, same edit, per N40's AC:** add `drop: false` explicitly to the package object.
   `drop` exists in the v6.2 struct as `bool`; its default is still NOT STATED IN DOCS; our
   bookings have always behaved as pickups. Sending it pins the behaviour we rely on.
3. **Decide `package_type_id`:** we send `7`; the v6.2 doc says "default 7, or **9** for regular
   packages in v6.2" and its example sends 9. What 9 changes is not documented and cannot be probed
   without booking. Keeping `7` is the conservative choice; ask the vendor what 9 means before
   switching.
4. **Docs after the code lands:** `specs/docs/KIRIMINAJA.md` — flip the "we call" row for booking,
   update the §Open-questions line (`destination_province_id` vs `destination_provinsi_id` is now
   answered: **neither** — the field names are v6.1's), and note the HTTP-400-on-error difference.
   `NEXT.md` N40 closes with a pointer here (left to the migrating session — that board is owned by
   other sessions right now).
5. **No change** to `apps/admin/lib/actions/shipping.ts` (`createShipment`), `shipment-payment.ts`,
   or any caller — the request shape and the fields we read back (`status`, `text`, `details[]`,
   `pickup_number`, `payment_status`, `qr_url`) are name-identical in the v6.2 docs.
