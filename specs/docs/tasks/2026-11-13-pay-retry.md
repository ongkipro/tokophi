# PAY-RETRY — "Bayar ulang" for a late or failed prepaid payment

- **Task:** `PAY-RETRY` (relates to `PAY-QRIS-EXPIRY`, route (3) of its findings)
- **Owner ask (2026-11-13):** "boleh bayar ulang untuk pembeli yang telat membayar, atau case-case yang bisa kamu riset"
- **Executor:** PayRetryAgent · branch `feat/pay-retry` · migration `0117_pay_retry`
- **Reference model:** AdsBookCMS `src/lib/autolaris-payment.ts` (`RETRYABLE_PAYMENT_STATUSES`, `effectivePaymentStatus`, attempts table). Ported as an idea, not as code: TokoΦ already anticipates several `payments` rows per order (AGENTS.md "ONE definition of the order's payment"), so an attempt is simply a new `payments` row. No attempts table, no hourly sweeper.

## What was true before this change (evidence)

## Cases → decision → why

| # | Case | Decision (v1) | Why |
|---|---|---|---|
| 1 | Entry point: how does a late shopper get back? | The same `/checkout/sukses` page on the same device (`localStorage.lastOrder` survives the tab). On expiry — or when the first bill never started — it shows **"Buat tagihan baru"**. Another device: unchanged, the Seller re-bills from the order screen (now unblocked, case 9). | No order-status page or token existed; building a cross-device order page is a larger product decision (owner question O2). |
| 2 | Who may ask? | A **one-order secret** (256 bits, `base64url`) minted by `/api/public/order` for prepaid orders, returned once (`payToken`), kept in `lastOrder`; only `sha256` is stored (`orders.pay_token_hash`). Wrong token, unknown number, other store, COD, pre-0117 order → the SAME 404. | An order number is printed on labels and quoted in chats — it identifies, never authorises. Hash-only storage is the impersonation-grant pattern. One 404 for all = no oracle for which numbers exist. |
| 3 | New public route? | Yes: `POST /api/public/pay/retry` on the Seller app (where the gateway key lives). `readPublicBody`, per-IP limit 6/min, CORS, provider text never to the shopper, `storeSlug` in the body is the tenant selector (same reasoning as the other four). Added to `public-guard.test.ts` ROUTES and the storefront CSP list. | AGENTS.md "The public API" rules. |
| 4 | When is a new bill allowed? | Only when every instruction is `failed` or provably `expired`, the order is `baru` + `pending`, not COD, not paid, ≥15 min before the 24 h cancellation, and fewer than 5 attempts exist. One function, `retryDecision` (`apps/admin/lib/pay-retry.ts`). | At most ONE live bill per order means the shopper cannot be charged twice by design. |
| 5 | What is "expired"? | `instructionState`: `expires_at` past → expired; `expires_at` NULL (pre-0117, unparseable, provider call threw) → **unknown**, presumed payable for 24 h from issue (`request_updated_at`, else `placed_at`); an `in_progress` claim younger than 15 min → starting. Read at request time — no sweeper, no production writes. | A dead bill read as live costs a WhatsApp; a live bill read as dead costs a double charge. 24 h is the longest window this account has ever been given (`create_payment` +24 h). The 5 production `menunggu` QRIS rows from July–Nov read as expired from now on, with no data write. |
| 6 | Double tap / two tabs / retry racing the cron | The claim runs under the ORDER's row lock (`for update`) and inserts the new row `request_state = in_progress` before the vendor call (outside the txn). The second caller reads `in_progress` or the live row and gets that, never a second bill. `request_key = reff_id` puts the store-unique index behind the lock. | Proven: two simultaneous presses → 1 vendor call, 1 row; the mutation that drops the lock goes red. |
| 7 | An OLD instruction paid after a new one was issued | The callback already accepts it. New: once any payment of an order is PAID, its other `menunggu` rows become `gagal`; a collected payment the ledger did not credit gets a **`refunds` row** (`refundUncreditedPayment`, after `creditSaleForPayment`): "Pembayaran ganda" if the sale is booked on another payment, "Dibayar setelah pesanan ditutup" on a `batal`/`retur` order. Idempotent (open-per-payment index + `not exists`, so a replay after settlement does not reopen it). | The ledger's one sale decides which payment is "the" payment, so the result is deterministic whatever order the callbacks arrive in. The refund lands on Super Admin's existing Pencairan flow (0112). |
| 8 | PAID on an order the cron cancelled | Same refund path (case 7). The cron also now **waits** while an instruction is `live` or `starting` (an unknown one is not waited for — today's behaviour). | Cancelling under a payable QR is how a buyer pays for an order that no longer exists. Retries stop 15 min before the cutoff, and every instruction expires, so the wait is bounded. |
| 9 | Seller's own re-bill (`createOrderPayment`) | Reads the same `instructionState`: an expired `menunggu` no longer blocks; live / unknown / COD-pending / paid still do. Dead rows are marked `gagal`; the new row keeps `expires_at`. Order screen: "Kedaluwarsa" pill, "Berlaku sampai", read-only "Riwayat tagihan (n)", and "Buat tagihan" offered on an expired bill. | Same rule on every path. |
| 10 | Amount and fee | The new attempt **copies** `amount_idr`, `admin_fee`, `total`, `method`, `channel_code` from the previous attempt; `grand_total = total`. No recompute. | The shopper pays exactly the bill they agreed to at checkout (FINANCE.md: `buyerPayable` = order payable + our fee). A fee-schedule change after checkout does not move an order's bill; `orders` money columns are untouched. |
| 11 | Channel switch | **Not in v1**: same channel, and only while the platform still has it `enabled AND active` (else `channel_off` → seller). | Switching changes the fee (`payment-fees.ts`) and needs a channel picker on the page — owner question O1. |
| 12 | `reff_id` per bill | Attempt 1 = order number (unchanged); attempt n = `<order number>-n` (≤ 18 chars, inside the vendor's 30-char cap). The callback URL is signed per reference, so the callback binds to exactly that row. | AutoLaris may refuse a reused `reff_id`; the callback rejects ambiguous matches. |
| 13 | First bill refused vs. thrown at checkout | Refused (`rc != 00`) → the shell becomes `gagal` (retryable at once). Thrown (timeout, HTML 502) → stays `menunggu`, outcome unknown → no second bill until bounded. The checkout now sends the shopper to `/checkout/sukses`, which offers "Buat tagihan baru" for the refused case. | A thrown call may have created the bill before the socket died. |
| 14 | Stock / voucher / flash price | Untouched by a retry: consumed once by the order, restored (stock) by the cron's cancellation as before. A lapsed flash sale does not re-price: the order's lines are the price. | Nothing is double-consumed; verified by reading `/api/public/order` (all consumption is inside the order txn) and the retry route (writes only `payments`). |
| 15 | Tracking | No change: the HELD Purchase is released by whichever payment lands; a second payment re-runs `releasePurchase`, which is idempotent; delivery rows are unique per `event_id = purchase:{number}`. | Test: two PAIDs on one retried order → exactly one Purchase row, released. |
| 16 | Expiry shown in the wrong zone | `parseAlExpiry` reads the vendor's string as +07:00 on the server; the browser receives ISO with an offset. | Fixes the WITA/WIT countdown and the Safari `Invalid Date` for every prepaid order, retried or not. |

## Owner questions (defaults chosen; none blocks v1)

- **O1 — Channel switch on retry.** v1 keeps the channel. Allowing QRIS ⇄ VA means the fee moves (QRIS 0,7 % of omset vs VA flat), so the bill amount changes from what the shopper first saw. Want it?
- **O2 — Cross-device return.** v1 works on the device that checked out. A shareable "lihat/bayar pesanan" link (token in the URL, like the 7-day recovery links) would cover a shopper who switches phones — a separate page and a separate security review.
- **O3 — Refund amount for a double payment.** Follows 0112: `amount_idr` (pre-gateway-fee). For a duplicate the buyer also paid the admin fee twice; refund the full `total` instead?
- **O4 — Limits.** 5 attempts per order, retry closes 15 min before the 24 h cancellation. Change either?

## Not done / not verifiable here

- No AutoLaris call was made (sandbox or production). The `-n` reference shape is inside the documented cap and the character set production already accepts (`PHI-…`), but a live `/submit` with a suffixed reference is unproven until the first real retry.
- Whether the vendor still honours a QR past its `expired` stamp is unknown; case 7 is what makes that safe.
- The 5 stale production `menunggu` rows are not written to; they read as expired (case 5).
