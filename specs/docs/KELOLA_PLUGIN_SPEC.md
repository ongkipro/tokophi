> (`/crm`, `/crm/followup`, `/crm/pipeline`, `/crm/template`) is retired and its job moves to an
> external CRM, **Kelola** (`kelolatim.com`), delivered as the first plugin of a new TokoΦ plugin layer.

## 1. Kelola public API — what it is

A **partner integration**, not a general CRM API. Two inbound endpoints (we push to Kelola) and one
outbound webhook (Kelola pushes status back to us). There are **no** contact, customer, ticket,
ongkir, WhatsApp, list or read endpoints.

| Direction | What | Endpoint |
|---|---|---|
| TokoΦ → Kelola | a new order | `POST https://kelolatim.com/api/public/toko/order/{token}` |
| TokoΦ → Kelola | an abandoned checkout (lead) | `POST https://kelolatim.com/api/public/toko/lead/{token}` |
| Kelola → TokoΦ | order status / resi changed | webhook to a public HTTPS URL we register in Kelola |

### 1.1 Credentials

- Per **Kelola store**: a URL `{token}` + a **secret**, generated by the Kelola admin under
  *Toko → Pengaturan → Toko & advertiser*.
- The secret is shown **once**. Regenerating issues a new pair and the old URL answers **404**
  immediately.
- No bearer token, no API key header, no OAuth, no scopes. The `{token}` in the path selects the store;
  the HMAC proves possession of the secret.
- Both values are server-side only (for us: encrypted at rest, §4.4).

### 1.2 Request signing (inbound, and the same scheme on outbound webhooks)

```
x-timestamp: <unix ms, 13 digits>      (10-digit seconds also accepted)
x-signature: lowercase hex( HMAC-SHA256( key = secret, msg = `${x-timestamp}.${rawBody}` ) )
```

- Sign the **exact bytes** sent. Serialise once, sign that string, send that string.
- Timestamp skew > **±5 min** → `401 { error: "stale" }`.

```ts
// lazy: reference only — the real sender lives in the plugin worker (§4.3)
import { createHmac } from "node:crypto";
const body = JSON.stringify(payload);
const ts = String(Date.now());
const sig = createHmac("sha256", secret).update(`${ts}.${body}`).digest("hex");
await fetch(`https://kelolatim.com/api/public/toko/order/${token}`, {
  method: "POST",
  headers: { "content-type": "application/json", "x-timestamp": ts, "x-signature": sig },
  body,
});
```

### 1.4 `POST /lead/{token}` (abandoned checkout)

| Field | Type / limit | Req | Notes |
|---|---|---|---|

| `customerName` | string 2–120 | ✅ | |

If that phone ordered within the last **3 days**, Kelola marks the lead "already ordered" itself.

### 1.5 Responses

| HTTP | Meaning | Our action |
|---|---|---|
| 201 | stored → `{ ok, id, code, status }` | done; store Kelola `id` |
| 201 + `status:"batal"`, `duplikatDari` | Kelola judged it a duplicate of the same buyer's order within **48 h** | done — but see §3.3 |
| 200 `{ ok:true, duplikat:true, code }` | resend of a `code` it already has | done (our retry after a lost response) |
| 400 `{ error, path }` | invalid field | **do not retry**; dead-letter, show `path` to the seller |
| 401 `signature` / `stale` | wrong secret / clock skew | dead-letter as "kredensial salah"; `stale` → check host clock |
| 404 | token unknown (regenerated or disconnected) | dead-letter, mark the connection **broken** |
| 409 | Kelola-side (store inactive, connector removed) | retry later |
| 5xx / network | transient | retry with backoff |

Kelola writes before it answers, so 200/201 = stored. A lost response is safe to resend with the same
`code`. Kelola's suggested backoff: 1 m, 5 m, 30 m, 2 h, then stop and tell the store admin.

### 1.6 Outbound webhook ("Kabar ke partner") — documented, NOT consumed in v1

> v1 registers no receiver (§4.6). AdsBookCMS runs without one too. Kept here so a later receiver
> starts from the facts.

Registered in Kelola: *Toko → Pengaturan → Toko & advertiser → ⋯ → Kabar ke partner*. Public HTTPS only
(private/local IPs refused). "Kirim tes" sends a `tes` event.

Headers: `x-timestamp`, `x-signature` (same HMAC scheme), `x-kelola-event`, `x-kelola-delivery`.

```json
{ "versi": 1, "event": "order.status | order.resi | tes", "waktu": "…",
  "order": { "code", "status", "statusSebelumnya", "resi", "kurir",
             "payment", "total", "codValue", "updatedAt" } }
```

- Statuses: `menunggu proses dikirim selesai retur batal`.
- `order.resi`: waybill issued/replaced, `statusSebelumnya = null`. `tes` has no `order`.
- `order` is the state **at send time**, not at event time. Order of delivery is **not** guaranteed →
  last-writer-wins on `updatedAt`. Duplicates happen → dedupe on `x-kelola-delivery`.
- No buyer PII in the payload — match on `code`.
- Answer **2xx within 10 s**; redirects count as failure. Kelola retries 1 m, 5 m, 30 m, 2 h, 12 h, then
  marks the delivery "gagal" after 6 failures.

## 2. Gaps and unknowns (ask Kelola before building)

1. **Webhook secret** — "same HMAC scheme" is stated; that it is the **same secret** as the inbound pair
   is implied, not stated. Confirm.
2. **Rate limits** — undocumented. Assume low; the worker batches anyway.
3. **No read/lookup API.** Order lookup by `code` and a catalog API are "segera hadir". Until then we
   cannot reconcile; the webhook is the only way back.
4. **Who ships.** `ongkir: 0` = Kelola calculates, and Kelola issues `resi`/`kurir` — i.e. Kelola assumes
   it fulfils. TokoΦ also fulfils (KiriminAja, `bulkGenerateResi`, ledger debit). See §3.1.
5. **Payment vocabulary** — only `cod` | `transfer`. QRIS/VA has no own value.
6. **Versioning** — only `versi: 1` in the webhook body; no deprecation policy.
7. **Customer/contact sync, WhatsApp send, ticketing** — none exposed. Everything the current CRM
   screens do (pipeline stages, follow-up queue, WA templates) happens **inside Kelola's own UI**, not
   through TokoΦ.

## 3. Fit with TokoΦ — the decisions that block design

### 3.1 🔴 Fulfilment ownership (blocking)

A TokoΦ order already has ONE fulfilment path: KiriminAja booking → `cron-tracking` fills
`orders.awb` → `applyOrderStatusChange` is the sole writer of `orders.status`, with ledger + COD logic
behind it (`specs/docs/rules/order-ledger.md`, `shipping-cod.md`). Kelola's webhook *also* produces
status + resi. Two writers on one order = the double-ship / double-debit class of bug.

Options:

| | Kelola role | `orders.status` writer | Webhook effect |
|---|---|---|---|
| **A (recommended for v1)** | CRM/CS mirror only | TokoΦ (unchanged) | none in v1 — no receiver (§4.6). Push is one-way |
| B | Kelola fulfils | Kelola, via `applyOrderStatusChange` from the webhook | TokoΦ must skip KiriminAja booking for that store, ledger/COD rules re-derived — large |

Recommendation: **A**. It replaces the CRM (the actual request) without touching money or shipping.
B is a separate ADR if ever wanted. Under A we send the **real** `ongkir` with `gratisOngkir` derived
from the order, so Kelola never recalculates a price the shopper didn't pay.

### 3.2 Payment mapping

`payments.method` (the one definition of "the order's payment") → `"cod"` when COD, else `"transfer"`.
`codValue` = the amount the courier collects (the order total for COD), `null` otherwise. Push only
after the order exists in our DB: COD at creation, prepaid **only once its payment is `berhasil`**
(§4.4 — Kelola is create-only, so a prepaid order pushed unpaid goes stale there). Owner call §7.3.

### 3.3 Duplicate semantics differ

Kelola auto-cancels a "duplicate" from the same buyer within 48 h (201, `status:"batal"`). In TokoΦ
both are real orders. Under option A this only affects Kelola's view; record `duplikatDari` in
`plugin_kelola_orders.last_note` so the seller sees why Kelola shows `batal`. Never mirror it into `orders.status`.

### 3.4 Field mapping (TokoΦ → Kelola order)

| Kelola | TokoΦ source | Note |
|---|---|---|
| `code` | `orders.order_number` | idempotency key — never change it after first send |
| `date` / `waktu` | `orders.created_at` in WIB (`dayKey()` for `date`) | |
| `customerName` / `customerPhone` | order's customer snapshot; phone already canonical `62…` | |
| `address` `kelurahan` `kecamatan` `kota` `provinsi` `kodePos` | `orders.ship_*` snapshot (0042) | |
| `payment` `codValue` | §3.2 | |
| `ongkir` `gratisOngkir` | `orders.shipping_idr`; `gratisOngkir = shipping_idr = 0 && a free-shipping discount applied` | |
| `discount` | `orders.discount_idr` | |
| `berat` | sum of line weight from `products` (same box as the quote) | |
| `items[].sku` | `product_variants.sku`, **fallback to variant id** when SKU is null (field is required) | |
| `items[].name` `qty` `price` | `order_line_items` (price as charged) | |
| `utm` | **TBD** — `orders` has `channel` but no raw UTM columns today; check `checkout_sessions` / `analytics_events` at build time, else omit (never a rejection) | |

Lead mapping: `checkout_sessions` rows that become `ditinggal` (`abandoned_at` set) → `code` = session id,
`nilai` = cart value, `produk` = first/most-valuable line name, `halaman` = last path if recorded.
Phone is required by Kelola → sessions without a phone are not sent.

## 4. TokoΦ plugin layer — the AdsBookCMS ADR-028 contract, ported to Postgres

### 4.1 Scope — first-party "Plugin", not a marketplace

- A plugin is **first-party product code**, compiled in, written by us. No third-party code, no upload,
  no runtime for customer code. PRD's intent (curated, locked checkout) stands; ADR 0019 records the
  boundary and edits the PRD "No Apps / plugins" line in the same PR.
- Seller UI name: **"Plugin"**, at **Pengaturan → Plugin**, owner only — the same name and place as
  AdsBookCMS, so the two products read the same. Never "Apps", never "marketplace".
- **Dormant means zero effect** (AdsBookCMS ADR-027 §2): a store that never activates a plugin gets no
  outbound request, no rows, no menu entry, no checkout change. The only allowed cost is one indexed
  read of `store_plugins` in the post-order hook and the cron.

### 4.2 Code layout (same shape as AdsBookCMS)

```
apps/admin/lib/plugins/
  registry.ts          # PLUGINS = [kelolaPlugin]; activePlugins(storeId), activate/deactivate/uninstall,
                       # scheduleOrderCreated(storeId, orderId), runPluginCron(now)
  kelola/
    index.ts           # manifest: { id:'kelola', name:'Kelola CRM', description, settingsHref,
                       #             onOrderCreated, onCron }
    wire.ts            # PURE, ported verbatim from adsbookcms src/plugins/kelola/sync.ts:
                       #   kelolaOrderPayload, kelolaLeadPayload, signKelolaBody, kelolaLeadUrl,
                       #   normalizeKelolaWebhookUrl, maskKelolaWebhookUrl, connection-test classifier
    wire.test.ts       # the AdsBookCMS sync.test.ts cases for those functions, ported
    sync.ts            # Postgres side: push, record result, drain orders, drain leads, status reads
    sync.test.ts       # real Postgres (`_test` DB): dormant path, retry window, tenant scoping
```

Manifest type (AdsBookCMS `Plugin`, minus the D1-only fields):

```ts
type Plugin = {
  id: string; name: string; description: string; settingsHref: string;
  onOrderCreated?(ctx: PluginContext, orderId: string): Promise<unknown>; // after the response
  onCron?(ctx: PluginContext, now: Date): Promise<number>;                // count for the cron summary
};
type PluginContext = { storeId: string; settings: Record<string, unknown> };
```

**What differs from AdsBookCMS, and why (forced, not taste):**

| AdsBookCMS (one D1 per store) | TokoΦ (one Postgres, many stores) |
|---|---|
| `schema` steps run on activation, tables `plugin_<id>_*` created per store | Plugin tables ship in a **Drizzle migration** (shared tables, `store_id` + RLS). No `schema`/`schema_version` in the manifest |
| Uninstall = `DROP TABLE` | Uninstall = delete **this store's** rows in the plugin tables + its `store_plugins` row |
| `waitUntil` | `after()` from `next/server` (Next 16.4.3, present) |
| `plugins.settings` JSON incl. secret | `store_plugins.settings` (non-secret) + `secret_enc` via `encryptSecret` |
| env pair `KELOLA_ORDER_WEBHOOK_URL/_SECRET` fallback | **dropped** — multi-tenant; a platform-wide env pair would push every store to one Kelola |

### 4.3 Data — migration `0117`, hand-written, idempotent (`specs/docs/rules/migrations.md`)

```
store_plugins                                    -- AdsBookCMS `plugins`, + store_id
  store_id uuid not null → stores.id
  plugin text not null                           -- 'kelola'
  enabled boolean not null default false
  settings jsonb not null default '{}'           -- { webhook_url_masked, push_leads: false }
  secret_enc text                                -- encryptSecret(JSON{webhook_url, webhook_secret}, kelolaScope)
  secret_v int not null default 1                -- scope version, bumped on re-paste (mengantarKeyScope shape)
  connected_at timestamptz                       -- FIRST successful connection (kept on re-save, cleared on disconnect); nothing older is pushed
  broken_at timestamptz                          -- set on 401/404; cleared by re-saving credentials
  activated_at timestamptz, updated_at timestamptz not null default now()
  primary key (store_id, plugin)
  RLS: store_id policy like every store-scoped table

plugin_kelola_orders                             -- AdsBookCMS table of the same name, + store_id + claim/lease
  store_id uuid not null, order_id uuid not null -- NO FK to orders (a plugin never blocks the core)
  claimed_at timestamptz                         -- lease: the one sender currently allowed to POST
  synced_at timestamptz                          -- 201 / duplikat:true
  gave_up_at timestamptz                         -- 400 (bad field): never retried; seller sees `path`
  attempts int not null default 0, last_error text, last_note text   -- last_error is token-redacted
  primary key (store_id, order_id)
  RLS: store_id policy

plugin_kelola_leads                              -- same columns, keyed by checkout session
  store_id uuid not null, session_id uuid not null, claimed_at, synced_at, gave_up_at, attempts, last_error
  primary key (store_id, session_id)
  RLS: store_id policy
```

**Not added (deliberately):** no `orders.kelola_*` columns — AdsBookCMS added exactly those
(`0063`–`0065`) and removed them in `0066` (ADR-028): core tables must not carry one plugin's state.
No generic `plugin_deliveries` outbox — the work queue is **derived** (§4.4), so nothing is enqueued
inside the order transaction. No `plugin_inbound_events` — no receiver in v1 (§4.6).
The 7-day scan uses the existing `orders_store_placed_idx (store_id, placed_at)`; no new index on `orders`.

### 4.4 Flow

**When an order is eligible** (one SQL predicate, shared by the hook and the cron — never two copies):

| Payment | Eligible from | Why |
|---|---|---|
| COD | order creation | the order is real the moment it is placed |
| prepaid (VA/QRIS/e-wallet) | its payment reaches `berhasil` | Kelola is create-only (§1.5: re-push = `duplikat:true`, no update). A prepaid order pushed at creation would sit in Kelola as `menunggu` forever after it is paid, and one that expires (2 h QRIS window) would stay alive there — CS chasing dead or already-paid orders |

…and in every case: `orders.status not in ('batal','retur')`, `placed_at >= connected_at`,
`placed_at >= now() - 7 days`, no `synced_at`/`gave_up_at`. **This differs from AdsBookCMS** (it pushes
every order at creation); per the shared-fix rule the same staleness exists there — raise it on that
repo, do not silently diverge.

1. **Claim before the network (the gate against double send).** `after()` and the cron can fire for
   the same order in the same second. Every sender first runs ONE statement:
   `insert into plugin_kelola_orders (store_id, order_id, claimed_at) values (…, now())
    on conflict (store_id, order_id) do update set claimed_at = now()
    where plugin_kelola_orders.synced_at is null and plugin_kelola_orders.gave_up_at is null
      and (plugin_kelola_orders.claimed_at is null or plugin_kelola_orders.claimed_at < now() - interval '5 minutes')
    returning order_id`.
   One row back ⇒ this sender owns the POST for 5 minutes — so every Kelola POST carries
   `AbortSignal.timeout(15_000)`, far below the lease: a request that outlived the lease would let the
   next claimant send a second time. A timeout counts as a transient failure (lease released,
   `attempts+1`); zero rows ⇒ someone else has it, or it is
   done. Kelola's `duplikat:true` is the second net, not the first (same lesson as Mengantar's
   idempotency key, PR #460). Do not split it into a read then a write.
2. **Order hook** — `/api/public/order` calls `scheduleOrderCreated(storeId, orderId)` via `after()`
   **after `db.transaction(…)` has returned** (the txn opens at `route.ts:855`), never inside its
   callback — a rolled-back order must not be pushed. Only COD is eligible at this point (table
   above). Failure is caught and logged; it can never fail or delay the order. A `codeOnly` guard pins
   the call's position after the txn's close, proved red on a mutated copy first.
3. **Cron** — route `api/cron/plugins` (header-only `CRON_SECRET` via `lib/cron-auth.ts`,
   `recordCronRun`), every **15 min** (a `cron-tracking`-style sidecar, `?every=` cadence), so a paid
   prepaid order reaches Kelola within ~15 min of its payment. Owner pool, cross-tenant:
   - Only stores with `enabled and broken_at is null`; **every query carries an explicit `store_id`**.
   - Per store per tick: at most **20** orders + 20 leads, oldest first, backoff by `attempts`
     measured from `claimed_at` = the last attempt (5 m · 30 m · then every 2 h; never shorter than the
     5-minute lease) — so one store with a backlog cannot starve the rest.
   - Response handling (§1.5): 201/`duplikat` → `synced_at`; 400 → `gave_up_at` + `path`; 401/404 →
     set `broken_at` and **stop that store for this tick**; 409/5xx/network → release the lease,
     `attempts+1`.
   - **Leads** (AdsBookCMS `drainKelolaLeads`): only when `push_leads`; `checkout_sessions` with
     `status = 'ditinggal'` (never `aktif`), a phone, `recovered_at is null`, `abandoned_at` inside the
     same 7-day / `connected_at` window; same claim statement on `plugin_kelola_leads`. A lead that
     converts AFTER it was pushed is caught by Kelola itself (§1.4: same phone ordered within 3 days ⇒
     "already ordered"). Reuse the `ditinggal` sweep's predicate (`lib/data/checkout.ts`).
4. **Order detail panel** — only while the plugin is active: "Terkirim ke Kelola · <waktu>" / "Gagal:
   <last_error>" / "Menunggu pembayaran" (prepaid, not yet eligible) + **Kirim ulang** (`orders:write`;
   clears `gave_up_at`, runs the same claim).
5. **Settings** — as built: a **section of Pengaturan** (`/pengaturan?section=plugin`, the same deep-link shape as
   `?section=alamat`), not a new route, so the page map gains nothing. Owner only, capability `plugins:manage`:
   - Pengaturan → Plugin: list of compiled-in plugins with Aktifkan / Nonaktifkan / Hapus data
     (`useConfirm`), exactly AdsBookCMS's list.
   - Kelola page: paste webhook URL + secret (normalised, masked after save, never returned),
     **Tes koneksi** (AdsBookCMS trick: a deliberately invalid signed body → `400` = URL + secret
     accepted, `404` = unknown URL, `401` = wrong secret/clock), toggle leads (default off), sync
     summary (synced / failing / given up / outside the 7-day window), broken banner, and the UU PDP
     disclosure covering **orders and leads** (§4.5).
   - Deactivate keeps settings + rows; **Hapus data** deletes them (§4.2 table).

**Known ceilings — deliberate, stated so nobody mistakes them for coverage:**

- `// lazy:` **state after the push is never synced.** Kelola has no update endpoint; an order that is
  cancelled or returned AFTER it reached Kelola stays live there until CS closes it by hand. Upgrade
  path: an update endpoint from Kelola (ask — §2), or the deferred receiver (§4.6) for the other
  direction.
- `// lazy:` **a paid prepaid order reaches Kelola up to ~15 min after payment** (next cron tick; the
  creation hook saw it unpaid). `pay/callback` is a money path and is left untouched for a CS feed.
  Upgrade path: call the same `scheduleOrderCreated` via `after()` from the callback after it commits —
  the claim statement already makes a second sender harmless.
- `// lazy:` **7-day window.** An order not accepted within 7 days of `placed_at` (Kelola down a week,
  or credentials broken a week) is never pushed; the settings page counts these as "di luar jendela".
  Re-saving credentials after a shorter outage needs nothing — the window catches up on its own.
- `// lazy:` **no backfill before `connected_at`.** Orders taken before the store connected are never
  sent. Upgrade path: a bounded "Kirim pesanan lama (≤ 30 hari)" action, only if a seller asks.

### 4.5 Security & privacy

- Tenant-owned integration credential (ADR 0012, `store_tracking_channels` pattern). URL (it carries
  Kelola's `{token}` in the PATH) + secret sealed with `encryptSecret` under `INTEGRATION_TOKEN_KEY`,
  scope bound to store + plugin + version — `kelola:${storeId}:v${secret_v}`, same shape as
  `mengantarKeyScope` (`packages/db/src/mengantar-account.ts`). Never sent back to the browser; the
  page shows the masked URL only.
- The `{token}` is a credential in a URL: **every** log line and stored `last_error` goes through a
  redactor (reuse `redactKey` from `packages/lib/src/mengantar.ts`, or lift it to a shared module —
  don't copy it). `no-published-credentials.test.ts` stays green.
- **Lead push is opt-in per store** (`push_leads` default `false`) and sends only `ditinggal` sessions,
  never `aktif` (AGENTS.md abandoned-cart rules: the shopper may still be typing).
- `plugins:manage` is **owner-only** — it ships shopper name/phone/address to a third party. Classified
  in `rbac-census.test.ts`; `admin` is derived by subtraction, so exclude it there explicitly.
- Pushing shopper PII — name, phone and address on **every pushed order**, plus abandoned carts when
  leads are on — to a processor is a **UU PDP** disclosure: the connect
  screen says so, and the storefront privacy page needs a processor line. Owner sign-off before launch.
- Kelola's error text stays seller-side (ADR 0004 pattern); nothing from Kelola reaches a shopper.
- Brand: "Kelola" is shown to the **seller** (a tenant-chosen integration, like Meta) and never to a
  shopper — check `packages/lib/src/provider-label.test.ts` scope when adding copy.

### 4.6 Deferred (not v1)

- **Inbound webhook** (§1.6, Kelola → TokoΦ status/resi). Under option A it could only ever be an
  annotation, and AdsBookCMS ships without it. If wanted later: a route under `api/public/plugins/`,
  raw body via `readPublicBody`, HMAC `timingSafeEqual`, ±5 min, dedupe on `x-kelola-delivery`,
  last-writer-wins on `updatedAt`, results in a `plugin_kelola_*` table — **never** `orders.status`.
  That PR must also add the route to the hardcoded `ROUTES` list in
  `apps/admin/lib/public-guard.test.ts` (HMAC over the raw text `readPublicBody` returns), update the
  public-api rule + `SECURITY.md` §1, and carry a `codeOnly` guard that the route writes no `orders`.
- Backfill before `connected_at` / beyond 7 days (AdsBookCMS has `now = null` for it) — only if a seller asks (§4.4 ceilings).

### 4.7 Keeping the two products in sync

- `kelola/wire.ts` is a **port of AdsBookCMS's pure functions**; its header names the source file and
  commit. A change to the Kelola wire format is made in **both** repos (owner rule: shared fixes go to
  the product too). Field additions over AdsBookCMS (`kelurahan`, `gratisOngkir`, SKU fallback to the
  variant id) land only if Kelola's API accepts them, and then in AdsBookCMS as well.
- Same settings shape (`webhook_url`, `webhook_secret`), same connection-test messages, same menu
  name, same manifest fields. A merchant moving between the products re-pastes the same pair.

### 4.8 As built (PR 1, 2026-11-13) — where the code differs from the text above, the code wins

- **Leads wait for the storefront's sweep.** A session is pushed only once it is STORED as `ditinggal`, and the
  aktif→ditinggal flip is the storefront's opportunistic sweep (`checkout-session.ts`), which runs only while
  that store receives checkout traffic — a quiet store's leads wait for the next shopper. Accepted ceiling;
  upgrade path is moving that sweep into a cron.
- **`saveKelolaConnection` stores nothing unless Kelola accepted the signed test** (400 on an empty body =
  URL + secret valid). An empty secret on re-save keeps the stored one. The tenant transaction is NOT held
  across the test call: the action runs each statement in its own `withTenant`.
- **"Kirim ulang"** clears a give-up, ignores the 7-day window and `connected_at`, keeps the payment/status
  rule and the 5-minute lease. Keyed on the order NUMBER (the detail route), resolved under RLS.
- **The order hook is wrapped in try/catch**: `after()` throws outside a request scope, and the order is
  already committed at that point — a throw must not become a 500. The cron covers anything it skips.
- **`gratisOngkir` and `kelurahan` are sent** (Kelola accepts both, §1.3); AdsBookCMS does not send them yet —
  the same `ongkir: 0` re-pricing defect exists there (shared-fix rule: raise it on that repo).
- `redactKey` moved to `@tokophi/lib/redact` (re-exported from `mengantar.ts`) — one sanitiser for every
  provider whose token rides in a URL.

## 6. Acceptance (v1, option A)

- **Dormant:** a store with no `store_plugins` row → placing an order makes no outbound request and
  writes no plugin row (test, real Postgres).
- **Tes koneksi:** wrong secret → "Secret tidak cocok…" (401); unknown URL → 404 message; correct pair
  → "Terhubung". Nothing is activated by a failed test.
- A storefront COD order appears in Kelola under the same `order_number`, real ongkir, SKUs, WIB date.
- Kelola unreachable during checkout → the order still succeeds and returns as fast as before; the cron
  pushes it later inside the 7-day window.
- Prepaid order: not pushed while unpaid; pushed within one cron tick after `berhasil`; an expired /
  `batal` prepaid order is never pushed.
- Double send: hook and cron racing on one order (forced, `pg_sleep` trigger like `users.test.ts`) →
  exactly one POST.
- Rolled-back order txn → nothing pushed; `codeOnly` guard on the `after()` position, proved red first.
- One store answering 401 → marked broken, skipped; another store in the same tick still pushes.
- Re-push of the same order → Kelola answers `duplikat:true`, row marked synced, nothing doubled.
- Abandoned checkout with phone → Kelola lead; without phone → not sent.
- Tenant: store A's cron pass never reads or pushes store B's orders/sessions (test with two stores).
- `wire.test.ts` carries the ported AdsBookCMS cases and passes unchanged.
- No write to `orders` from any plugin path (`codeOnly` guard over `lib/plugins/**`).
- `npm run verify-migrations` + `npm run verify-rls -w @tokophi/db` green with the 3 new tables;
  `npm run test:db`, `npm run lint -w @tokophi/admin`, `npm run build:admin` green.
- Pengaturan → Plugin + Kelola page + order panel driven in a real browser (prod build, `next start`),
  narrow + wide, 0 console errors.
