The order is a safety property, not a preference

The six compose — but not in any order. There is exactly one real merge conflict in the whole set, and it has a required direction: wt-sec must land before wt-fix2, or the person resolving it is one careless click away from re-introducing a published owner password.

Recommended order

flowchart LR

  S --> SEC["3 - wt-sec<br/>lands the guard<br/>no-fixed-password.test.ts"]
  SEC ==>|"REQUIRED: sec BEFORE fix2"| F["4 - wt-fix2<br/>resolve actions.ts here<br/>drop your hunk for that file"]

  DB -->|"db first: order-actions owns N9"| OA["6 - wt-order-actions<br/>stock + money write paths<br/>deploys last and alone"]

The rest is risk ordering: perf is the smallest surface and inherits nothing; seo is the largest storefront change and was validated on top of perf; order-actions is the only set touching stock and money write paths, so it deploys last and alone, making a rollback unambiguous.

Merges are serialised here — each triggers a Coolify build — so merge one, watch the deploy land, then release the next. Do not re-apply saved plain diffs onto a moved base; that is the one path where NEXT.md collides unnecessarily.

Why wt-sec must precede wt-fix2

Both orders produce exactly one conflict, in the same file, with the same correct resolution. They are not equally safe.

✓ sec first — correct

fix2's author opens the conflict and finds their entire actions.ts change already present — the four timestamp edits merged silently because they are byte-identical. The resolution is “drop my hunk for this file”, which is obvious and hard to get wrong.

And no-fixed-password.test.ts is already in the tree, so a wrong resolution fails immediately.

✗ fix2 first — dangerous

sec's author must delete DEV_PASSWORD and a comment block a colleague wrote 20 minutes earlier — which looks like reverting someone's work — and the guard that would catch a half-resolution is arriving in the same PR being resolved.

A “keep both, take theirs for the comment” resolution silently restores hashPassword(DEV_PASSWORD). That is the published-owner-password bug, back.

wt-db before wt-order-actions is the second positional constraint, and a softer one: their NEXT.md hunks share context lines (N8's body is order-actions' leading context for N9). Three-way merges clean either way, but the second to land inherits the N8/N9 adjacency — and order-actions' author owns N9, so they can also fix the dangling “the count above was seven” sentence, which no longer has a count above it once the heading is rewritten.

What did NOT conflict — and this is the important part

All four timestamp edits — dropping createdAt: ANCHOR on accounts, dropping it on stores, acceptedAt: ANCHOR → new Date(), dropping updatedAt: ANCHOR on store_stats — are byte-identical in both worktrees, so git merges them silently. The two agents independently wrote the same fix, character for character.

Which version wins: wt-sec, wholesale. It is a strict functional superset for this file. Taking wt-sec's actions.ts verbatim loses nothing functional from wt-fix2; it loses only wt-fix2's comment prose, which contains one fact wt-sec's does not — that an anchored store drops out of newSignups30d, the platform's own new-signup count. Graft that one sentence in if you want it; do not graft the code.

  • ✅ Trial length unchanged. BILLING.TRIAL_DAYS is 3, so the expression is equivalent to the old 3 * 86_400_000.

Three problems found — none of them in the product code

1 · a coin-flip check

check-pdp-srcset.mjs is ~50% flaky

Four consecutive runs against the same build, unchanged DB: PASS, PASS, FAIL, FAIL. Same 2-of-4 split on the six-way tree; not caused by wt-perf.

Cause: thumbnail #1 and the main gallery image are the same URL with the same srcset. The main image (380 px box) legitimately fetches the 800 w candidate; whether Chromium then reuses that cached file for the 66 px thumbnail is a timing race. When it does, the check reads currentSrc = 800w and calls it a 6.1× regression — but zero extra bytes were transferred; it is a cache hit.

The structural assertion (every thumbnail has srcset + sizes) passed 4/4 every time and is sound. Fix: exempt an <img> whose currentSrc was already requested by another element, or assert on transferred bytes.

2 · writes to shared state

check-h1-floor.mjs writes to the shared dev DB

It inserts a page_templates row for a store that has none and deletes it in finally at a fixed UUID. It cleaned up correctly here — count 2 before, 2 after, no leftovers.

But the fixed id means two agents running it concurrently delete each other's row mid-poll, finally does not run on SIGKILL, and while it runs a real store has a homepage it never built, visible to any concurrent reader. Consider gating it behind an explicit env var.

3 · the order itself

An unsafe merge order

Covered above. wt-sec → wt-fix2 is mandatory, and it is the only ordering constraint with a security consequence.

One convention worth deciding deliberately

Only wt-seo updated CHANGELOG.md. wt-perf ships a rendering change, wt-order-actions changes stock and payment reads, wt-sec closes a credential vulnerability, wt-fix2 changes twelve date computations — none added an entry, while AGENTS.md:68 says to record a contract-affecting change there. Because only one agent touched the file there is no merge risk today; had all five followed the convention it would have been a five-writer collision.
