What breaks if this is misunderstood

1. apps/admin is not only the Seller UI — it is the public API tier (E7). /api/public/order, /ongkir, /promo, /pay/callback and /api/uploads/[name] live inside it and are excluded from the auth middleware (middleware.ts:66). The admin container must be up for any shopper to check out, on a different origin — which is why every one of those routes carries hand-written CORS headers and a try/catch wrapper.

2. apps/landing having no database is a design decision, not an oversight. Adding a DB read to it removes the only surface that survives a Postgres outage.

Three shipped incident classes, all still live as hazards

  1. “RLS will scope it” on a table RLS does not scope. Before 0058, two functions doing .from(stores).limit(1) inside withCurrentTenant returned an arbitrary store — a merchant read a stranger's shop name, WhatsApp and subscription countdown, and because the paired write was correctly scoped, pressing Simpan would have renamed their own shop to the leaked one. The policy is the net; the WHERE is the rule.
  2. The child-table class. A write to any of the 12 tables lands regardless of tenant, and the parent write under RLS silently no-ops for a foreign id — neither half errors. verify-rls cannot see this class at all.
  3. platform_activity is the only intentional store-scoped gap — treating it as an oversight and “fixing” it would break the super-admin audit log.

Why impersonation is the open security decision

The exchange itself is well-built: the audience claim is what stops a stolen 7-day merchant session JWT (same AUTH_SECRET, no aud) being replayed at /impersonate, and the algorithm is pinned. But the asymmetry is the whole risk, and it is structural:

  • ▸ A 2-minute token buys a 7-day cookie. The short life of the exchange token bounds nothing after the redirect.
  • ▸ The minted session is indistinguishable from the merchant's own login. No aud, no imp claim, no operator id, no shortened expiry. Nothing downstream can tell an impersonated request from a real one. Only the mint is audited; every action taken during the impersonation is attributed to the merchant.
  • ▸ There is no revocation. No jti, no token version; a password reset does not invalidate an existing JWT. The one thing that ends it early is deleting the owner's store_users row — and the merchant cannot remove themselves.
  • ▸ role is taken from the store_users row, so an impersonated session is exactly as powerful as the merchant's own owner account — including settings:write, integrations:write (tenant secrets) and landing:html (raw markup that executes on the shop's origin).

Separately: apps/admin/middleware.ts:49-56 rewrites /store/{slug}/… and passes the slug as an x-tokophi-store header without validating it against the session's store. The comment says RLS enforces regardless — true for the 51 RLS'd tables and not true for the 12 child tables or any query that omits its storeId filter.

“Kecamatan PRICES, Kelurahan BOOKS” is only half implemented

kaShippingPrice posts only origin, destination, weight, item_value, insurance, courier — no subdistrict fields. Correct, and the rule holds.

But nothing books a destination kelurahan. kaCreateOrder supports destination_kelurahan_id; createShipment never passes it. orders.ship_kelurahan_id and ship_kelurahan_name are 0 / 842 filled, and checkout.astro:404 states outright: “The order API ignores kelurahan entirely”. Sender side likewise: sender_kelurahan_id is 0 / 7 filled. Both columns are dead.

Origin: the fallback is the default state

store_settings.sender_kecamatan_id is 1 / 7 filled — six of seven stores fall to the resolveArea(store.city) fuzzy fallback and are quoted with originFrom: "store-city". It is flagged in the response by design — but it is the default state, not the exception.

Two-stage quote: /ongkir quotes FAST_COURIERS = ["spx","jne"] on first paint (measured 0.5–0.65 s) and everything on all: true (5.45–5.5 s). /order re-quotes scoped to the courier the shopper picked.

page_templates.type ∈ {homepage, category, product} and the three are not interchangeable. A template with zero sections is treated as absent, so an empty save cannot blank a page. In the container right now there are exactly 2 templates: one homepage default and one product default — the category path is on the fallback everywhere.

The 14 section types: hero, product-listing, image-text, multicolumn, product-grid, category-nav, collection-bento, lookbook, banner-promo, marquee, testimoni, blog, rich-text, faq. The palette is narrower than the renderer, per type: homepage = 13, category = 10, product = 9.

Narrow the PALETTE, never the RENDERER

sections is jsonb — a template saved months ago can hold a section type no longer offered for its type, and if the switch stops handling it the section silently vanishes from a published, live storefront. There is no default: arm and no exhaustiveness assertion, so a type added to SectionConfigMap and forgotten compiles and renders nothing. (E8)

The other trap: product-listing is the real catalogue (server sort, 12-per-page pagination, empty state); product-grid is a flat slice capped at limit. Offering only the second on a category template silently truncates a merchant's catalogue.

Journal archaeology — 88 tags ever recorded, 86 today

By replaying all 79 historical revisions of _journal.json. Two are gone:

TagFateConsequence at the time
0046_good_dustjournal entry whose .sql was never committedEvery fresh drizzle-kit migrate died; production never created the kelurahan table and /api/public/ongkir 500'd on every checkout.

Both are resolved, and both prove the point: verify-migrations checks the journal against itself and is blind to an entry that was removed or renumbered — a journal missing an entry is perfectly self-consistent.

One transaction, whole batch. Drizzle applies the whole pending batch in ONE transaction. A single “already exists” rolls back every migration behind it and prints nothing. On 2026-07-30 that left 16 migrations unapplied on the shared dev DB. Hence: every migration must be idempotent.
A non-increasing when makes drizzle SKIP a migration while reporting success. That is check #1 in verify-migrations.ts:49-59.
The seed is not a migration. It runs on every deploy but does not overwrite data an existing store already has, so a seed change reaches new stores only — invisible on dev, live in production.

The container has 92 rows in drizzle.__drizzle_migrations — six more than this branch has entries, because it is shared with sibling worktrees. Count files on your branch, not rows in the container.

9 · What the architecture mapper could not verify

Stated plainly, because a confident wrong entry is worse than a gap.

  1. Which deployment target is live. The two docs contradict each other. No SSH to any VPS, no production query, no DNS touched.
  2. Whether RLS actually blocks a cross-tenant read at runtime. The mechanism was confirmed statically (policies exist, tokophi_app has rolbypassrls=f, withTenant issues set local role) but verify-rls / verify-rls-app were not run here — both connect and could interfere with sibling agents. The “11/11 green” claim in AGENTS.md is unverified by this mapper.
  3. The COD-on-SPX return-leg belief. A commercial fact about KiriminAja, not something in the code. Remains unverified.
  4. KiriminAja / AutoLaris live behaviour. No provider call was made. KIRIMINAJA_ENV defaults to sandbox; whether production sets it is unverified.
  5. accounts tenancy. No store_id, no RLS; not established as platform-level or store-scoped, so it is not counted in the 12-table child class. Someone should settle it.
  6. The impersonate route in production. Fully mapped from source, but not exercised end-to-end in a browser; cookie behaviour across real subdomains is asserted by code comments, not measured.
  7. Whether the 12 child tables are all reached only through correctly-scoped parents today. The class and the rule were verified; auditing all 40 action files' call sites is separate work that was not done.
  8. Runtime behaviour of anything. No dev server started, no page rendered, no browser driven for this document. Everything above is source + catalog.
