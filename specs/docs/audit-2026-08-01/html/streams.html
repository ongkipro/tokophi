Verified by pixel A/B over 40 rating widgets: DPR 8 and DPR 2 byte-identical; DPR 3 differed on 8 of 40 by 1–2 pixels out of 45 288, max channel delta 5/255, all on the fractional-fill clip edge. The cross-validator re-ran it and found 36/36 identical at DPR 1 and 2 — if anything the original claim was pessimistic.

One characterisation was overstated and has been corrected

“393 of 1023 were <svg>+<path> and 312 of those were stars” — 393 is the whole SVG namespace, <svg>+<path> is 383, and 312 is the widget's total element count, not its SVG share (240). Reads as 79% where the truth is 61%. The headline numbers are exact; the wording was headed into AGENTS.md and has been corrected.

Honest limit stated: 915 is under Lighthouse's 1400 median but over its 800 p10 — the audit improves without passing.

Refused, with numbers

The client build target is already esnext (Astro hard-codes it; no build key; no browserslist in the repo). There is also no bundle to trim — dist/client contains zero .js files; all first-party JS is inline.

The 44 KiB unused-javascript and 12 KiB legacy-javascript are Meta's fbevents.js: 188.8 KB unused of 394.5 KB (47.9%), bundling core-js v3.32.2 — the exact signature the audit detects. A build-target change would have a measured delta of 0 bytes.

wt-seo

Headings, sitemap, image bytes

N11 — confirmed, and worse than stated

A builder homepage without a Hero rendered zero <h1>; a homepage with a Hero rendered three (the carousel emitted one per slide).

Fixed: slide 1 keeps <h1>, slides 2..n become <p>; a Hero-less homepage gets <h1 class="sr-only"> carrying the store name from the DB, never invented copy. SectionRenderer untouched — still switches on all 14 types, nothing published can stop rendering.

Verified: 13 pages across 5 stores, all h1=1. Cross-validator re-verified 3→1 and 0→1 independently against a fresh build.

N13 — confirmed, but its stated data source does not exist

products.updated_at is not in schema.ts and not in information_schema; collections has neither timestamp. So <lastmod> was emitted only where a defensible timestamp genuinely exists — pages.updated_at is real and stamped on every save, so /halaman/* got one (N13 did not even ask for it). Products and categories deliberately get none.

Why created_at was rejected — a reason worth keeping

A product created in March and re-priced today would advertise March — the page most needing a re-crawl marked as the stalest — and Google discounts lastmod site-wide once it finds it inaccurate, which would take the honest blog and page dates down with it.

Sitemap: 55 URLs, 21 with <lastmod> (from 15), all YYYY-MM-DD, none in the future, every value reconciled against SQL.

closes the one blocking error

wt-db

N8 backfill — correctly refused

docs only, no code

NEXT.md said “77 rows on production”. That was the dev count. Production has 75 orders total and 65 nulls, and not one has a ship_postcode. Every derivation named in the task resolves zero rows there.

Two structural discoveries behind it

  1. The id spaces cannot be joined. orders.ship_kelurahan_id is an integer (KiriminAja village id); kelurahan.id is a text BPS/Kemendagri code (34.02.13.2004). Village → district is not derivable locally at all.
  2. Two migrations were lost to number collisions. ship_kelurahan_id / ship_kelurahan_name exist on the shared dev DB but in no migration and not in schema.ts; slots 0034 / 0049 now belong to another branch. verify-migrations is green because the journal is self-consistent — which is precisely why the loss was never flagged. Consequence: seed:recent cannot run against production (it selects a column production does not have) and is green on dev only because of push drift.

The trap avoided

The 62 dev postcodes are fabricated by the seed (POST_OF[city] + 3 random digits); 59 do not exist in kelurahan at all. Backfilling from them would have written a confident wrong kecamatan and silenced destinationGuessed (#117) — strictly worse than NULL.

Rows stay NULL and stay flagged.

Validated on synthetic fixtures inside a rolled-back transaction: unique pair → backfilled, 3-district postcode → left NULL, already-set → not overwritten, second run → 0 rows.

Unverified — every production figure here (75 orders, 65 null, column absent, 0 postcodes) was taken by the agent that ran it. The cross-validator had no prod access. Nothing contradicts them; everything checkable against the local DB matched to the row.

wt-order-actions

Tenant scoping + payment ordering

N9 — NEXT.md said 7 copies across 4 files. There were 8.

The eighth is apps/admin/app/api/public/order/route.ts, which had no store_id and runs as the owner with RLS off — and inventory_levels is keyed (variant_id, location_id) with two independent FKs, so nothing forces a variant's inventory row to sit at a location of its own store.

Extracted to lib/default-location.ts with storeId as a required parameter — forgetting the tenant is now a compile error. All 8 sites verified scoped; the emitted SQL carries loc.store_id; tsc clean.

⚠ Correction to NEXT.md's framing

Its claim that “only the last one carries the tenant filter” is false — products.ts:91 and :135 carry it too, and the 4 join-based admin copies run inside withTenant where locations is RLS'd. The genuinely exposed sites were 2: order-status.ts (reached by ka-tracking.ts on the owner connection) and the public order route. Treat N9 as a duplication task with two real security sites, not seven.

The actions that genuinely still throw merchant-facing strings are customers.ts (×3), crm.ts (×3), checkout.ts (×2) and cancelPurchaseOrder — recorded, not touched.

read-only

Measurement stream — production, no change set

N3 — the question was wrong, not the answer

15 desktop runs: median 99, range 55–100, TBT = 0 in all fifteen. Bytes and request count identical every run (26 requests, 302 KB). Pearson r(score, network-RTT) = −0.866; runs ≥95 averaged 64 ms RTT, runs <95 averaged 632 ms. The score is a proxy for the measuring machine's link quality.

Refused to compare 99 against the old 84 — different machine, different day, incomparable populations.

Recommendation: drop desktop as a KPI or pin it to a fixed measurement host. → D5

N4 — cause found: the hero carousel's autoplay

Speed Index scores every frame against the last frame; an autoplaying carousel guarantees the last frame differs, so the page is scored as never visually complete. Controlled A/B, one Chrome flag, everything else identical:

SI medianPerfLCP
autoplay ON7.96 s67 / 90 / 881.81–2.09
autoplay OFF1.87 s98 / 97 / 971.82–1.89

Ruled out with evidence, not assumption: marketing pixels load at 10 780 ms, after the 10 114 ms visual change, and the frame pair during which all three vendor bundles execute shows 0.00% pixel change; CLS 0.000 across all 21 runs; font swap is 167 ms; no client islands on the homepage.

Recommendation: do nothing, record it. The page is genuinely complete at 1.8 s. Chasing the number means delaying the cross-fade past the audit window — buying score with a carousel that feels dead on arrival. prefers-reduced-motion was used as an instrument, not a proposal. → D6

N12 — the claim was wrong; a real bug sat behind it

Uploads do get width variants (?w= returns genuinely different bytes: 3 578 B @200 → 61 074 B full), the route sets immutable itself and goes cf-cache-status: HIT, and app./toko. share anycast IPs, one wildcard cert and HTTP/3 so Chrome coalesces — Lighthouse offers zero preconnect savings.

The real finding was the PDP thumbnails, above. A full read-only sweep of all 276 text/jsonb columns found page_templates.sections contains zero /api/uploads references — no store currently uses an uploaded hero, so the ladder gap was pre-emptive.

Architecture map — 9 diagrams, no change set

Every non-obvious claim carries file:line or a SQL result. Counted from the code and catalog, not quoted from docs. Highlights beyond E7:

  • Real counts today: schema.ts = 77 tables; the container has 78. 51 tables carry store_id, 50 have RLS, sole deliberate exception platform_activity.
  • The child-table class is 12, not 11 — AGENTS.md omits flash_sale_items. That class has produced five shipped cross-tenant bugs.
  • Impersonation, mapped end to end: a 2-minute token buys a 7-day cookie, the minted session carries no impersonation marker at all, there is no revocation, and a password reset does not kill it.
  • “Kecamatan PRICES, Kelurahan BOOKS” is half implemented. ship_kelurahan_id/_name are empty in 842 of 842 rows; sender side empty in 7 of 7 stores.
  • 6 of 7 stores have no sender_kecamatan_id, so every quote for them falls back to a fuzzy match. Flagged by design — but it is the default state, not the exception.
  • Journal archaeology: 88 tags ever recorded, 86 today. Both losses prove verify-migrations checks the journal against itself and is blind to an entry removed or renumbered.
  • 20 doc/code disagreements tabulated. The most dangerous is not in a doc at all: apps/admin/lib/tenant.ts:23-25 is a code comment that is wrong twice — it says “36 tables” and says stores has relrowsecurity = false, which migration 0058 made false. It sits in the file that defines the tenant boundary.
