E1

Every store created from Super Admin got the owner password tokophi123

✓ FIXED  wt-sec
apps/super-admin/lib/actions.ts:27 apps/super-admin/lib/actions.ts:107

apps/super-admin/lib/actions.ts:27,107 hashed new owners' passwords from the DEV_PASSWORD constant — a string published in this repository and in AGENTS.md.

const DEV_PASSWORD = "tokophi123"; // default local password for provisioned owners/admins
...
const [u] = await tx.insert(schema.users).values({ email, name: ownerName,
  passwordHash: hashPassword(DEV_PASSWORD) }).returning();

The failure

An operator onboards budi@tokosaya.com; anyone knowing that email logs in at app.tokophi.com as store owner → every order (buyer name, WhatsApp, full delivery address), every customer record, and via settings:write the bank-account and payout actions. Nothing forces a change and nothing expires it. createStore also did not return the password, so it was never handed to the merchant either: the account was unusable to its owner and usable to anyone who guesses.

The same bug had already been fixed 250 lines below in invitePlatformAdmin (random tempPassword(), revealed once) — whose own comment asserted the other paths were already correct. Instance patched, class missed.

Status: fixed in wt-sec

createStore now mints a random password and returns it; the operator sees it once via a persistent toast (a dialog was rejected because the handler router.pushes immediately and would unmount it; <Toaster> lives in the root layout and survives navigation). Proven on tokophi_test, rolled back: verify('tokophi123') = false, verify(minted) = true.

A class-level test (no-fixed-password.test.ts) scans the action module and fails if any hashPassword() call receives anything but a freshly minted value, if a minting action fails to return it, or if any write is anchored to a frozen date — proven red (3/5) before green.

Related: D9 — tempPassword() entropy is 24 bits and no login rate-limit was found. And whether E1 has been exploited in production is UNVERIFIED.

E3

The abandoned-cart recovery link is never minted

◑ NOT WIRED, DELIBERATELY
apps/storefront/src/lib/recovery.ts:43 apps/admin/lib/data/checkout.ts:182,205

signRecoveryToken has zero callers; none of the 6 wa_templates rows contains a link placeholder or URL; cartMessage fills only {nama, produk, toko}.

The failure

The merchant's WhatsApp message contains no way back. The shopper must start over. And ~50 lines of storefront code — verifier, “Selamat datang kembali” banner, cart restore, field pre-fill, kecamatan restore — are unreachable. Independently confirmed twice.

Meanwhile the docs claimed it worked: REQUIREMENTS.md SEC-13 = MET, UI_INVENTORY.md:60 = “✅ real DB”, CODE_MAP.md:113 = “mints/verifies”, STATUS.md:162 = “Recovery links are signed, not guessable”. This is the exact failure mode STATUS.md's own opening rule describes.

Status: not wired, deliberately — docs corrected instead

Wiring it is not small: the signer lives in apps/storefront/src/lib, which the admin cannot import (needs a move to packages/lib); the read layer does not fetch the store slug; the template needs a {{link}} no existing row has (and the seed is not a migration); and the restore path has never been run in a browser.

Four docs corrected — SEC-13 is now VACUOUSLY MET — NO LINK IS EVER MINTED, which separates what is true (no raw-id path exists; the verifier is correct and store-bound) from what is not. BACKLOG.md P1 records the four concrete steps and restates the security shape: signed, store-bound, 7-day jose token, never a raw session id.

The two writes

E5

desc() in drizzle emits bare DESC, which is NULLS FIRST in Postgres

✓ FIXED  wt-order-actions
apps/admin/lib/data/order-detail.ts:306 apps/admin/lib/data/orders.ts:234

data/order-detail.ts:306 used desc(payments.paidAt) while data/orders.ts:234 used paid_at desc nulls last. Both files carried comments asserting they matched — the detail one reads “Must match the LIST's definition exactly … unpaid last … One order, one answer.”

The failure — a display defect

On an order with one unpaid and one paid payment, the list names the paid method and the detail names the unpaid one — the merchant reads two different payment methods for one order, depending on which screen they are on.

⚠ Corrected 2026-08-01, after the source record's first draft

Both data files' comments claim this fact feeds createShipment's courier cash-collection instruction (COD vs VA), and the source document initially repeated it. It is false, and it was checked against the code: apps/admin/lib/actions/shipping.ts:512 derives COD independently, via exists (select 1 from payments p where p.order_id = … and p.method = 'cod') — an existence test that no ordering can affect. E5 is a display defect, not a money or shipping defect, and its severity is lower than first written.

Note what that means: the comments asserting the link are themselves wrong, in the same two files whose comments already wrongly asserted the two orderings matched. The same files carry two false comments each — the bug was in the code, and so was the misleading explanation of its severity.

Reproduced against real Postgres before the fix: list -> cod, detail -> va, DISAGREE — two screens naming two methods for one order.

Latent, not live: 827 payments, 46 with paid_at IS NULL, but 0 orders currently carry both shapes. This item was listed under “✅ Closed this session — do not redo” in NEXT.md; it was not closed.

Status: fixed in wt-order-actions

One exported latestPaymentFirst() used by both paths, with a real-Postgres test proven red then green.

Same class, lower stakes and NOT fixed: data/articles.ts:57 sorts every draft above every published post in the seller's Blog list.

E6

tokophi_app holds full DML on platform tables with RLS off

✗ NOT FIXED  design decision

platform_cod, platform_couriers, platform_payout, platform_payment_channels, plans — and the stores policy is FOR ALL, so the tenant role can UPDATE its own comped / status / trial_ends_at.

platform_payout           | DELETE,INSERT,SELECT,UPDATE   (rowsecurity = f)
platform_cod              | DELETE,INSERT,SELECT,UPDATE   (rowsecurity = f)
platform_couriers         | DELETE,INSERT,SELECT,UPDATE   (rowsecurity = f)
platform_payment_channels | DELETE,INSERT,SELECT,UPDATE   (rowsecurity = f)
plans                     | DELETE,INSERT,SELECT,UPDATE   (rowsecurity = f)

The failure

Latent today; live the moment a merchant JWT drives that role, which is exactly the stated production architecture (PostgREST as tokophi_app with the store_id claim feeding the GUC). At that point a merchant's own JWT reaches a role that can UPDATE platform_cod SET max = … or UPDATE stores SET comped = true. verify-rls structurally cannot see this — it derives coverage from store_id columns and these tables have none.

Owner decision required before the VPS cutover. The shape of the fix would be REVOKE INSERT, UPDATE, DELETE ON platform_* FROM tokophi_app plus column-level grants on stores. → D4

E15

apps/admin ESLint: 19 errors / 23 warnings, pre-existing

● RECORDED

12 are “component created during render” (both sites stateless — cosmetic), 5 setState-in-effect, and 2 are false positives (async server components deliberately calling Date.now()).

Was 28 errors on 2026-07-31 — someone has been fixing them. next build does not run ESLint, so nothing catches this automatically.

Reported as checked-and-fine — the negatives that are worth as much as the findings

  • Stock: the FOR UPDATE lock reads the same row the decrement writes, quantities aggregated by variant before locking, variants locked in sorted id order, no GREATEST(…,0) clamp. Correct.
  • Payout: pg_advisory_xact_lock(hashtext(storeId)::bigint) — the legal replacement for the sum() … FOR UPDATE Postgres rejects. Correct.
  • Ledger: creditSaleForPayment excludes batal and retur; double-credit enforced by partial unique indexes. Correct.
  • COD: derived from the order's own fact, and createShipment refuses a caller whose input.cod disagrees. Not affected by E5.
  • Client <script> blocks: all 27 extracted and linted for no-undef with browser globals — zero errors. The queueSave is not defined class is clean today.
  • Checkout, driven in a browser: en-US locale, real add-to-cart, real rate load, 0 pageerrors, 0 console errors, Rp 110.000 + Rp 15.700 = Rp 125.700.
